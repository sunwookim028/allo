##################################################
Tutorial: A PyTorch MLP on TinyTPU, Then Change It
##################################################

This tutorial takes a two-layer PyTorch MLP, compiles it onto the TinyTPU
with ACT, and runs it on the TinyTPU design itself. Then it changes the
machine twice and runs the same model again:

#. **A parameter:** a larger systolic array. One environment variable.
#. **An instruction:** a new fused ``mvoutrelu``, added to the ISA, the
   hardware and the compiler. Four small patches.

After each change ACT recompiles the unchanged model for the new machine,
and the result is checked byte for byte against PyTorch. Nothing on this page
needs Vitis. Every output shown is a real run, regenerated by
``make tutorial-outputs``.

.. code-block:: text

    PyTorch nn.Module                 workloads/models.py
      -> AlloTracer + torch.fx        workloads/extract.py     shapes and ops
      -> one workload spec per layer                           act/corpus/'s JSON
      -> ACT mapspace search          act/search.py, act_target.py
      -> a TinyTPU program                                     checked on isa_ref
      -> the design, simulated        ip/, df.build(target="simulator")
      -> compared with PyTorch        workloads/run.py

Paths are relative to ``examples/tinytpu/``. The flow and its design choices
are explained on :doc:`workload_suite`, the machine on :doc:`tinytpu_isa`.


Setup
=====

Once per checkout. The ``allo`` conda environment, ``torch`` (optional
upstream, required here) and this checkout's own MLIR bindings:

.. code-block:: bash

    conda activate allo
    pip install --index-url https://download.pytorch.org/whl/cpu torch==2.14.0
    export LLVM_BUILD_DIR=/path/to/llvm-project/build   # the env does not set it
    examples/tinytpu/reproduce.sh --no-cosim   # builds mlir/build, runs the gates
    cd examples/tinytpu

The ``Makefile`` exports ``LLVM_BUILD_DIR`` and ``OMP_NUM_THREADS`` if they
are unset, and falls back to ``conda run -n allo`` when the shell's ``python``
cannot import ``allo``.

Run it
======

.. code-block:: bash

    make mlp                  # ~10 s: compile, build the design, run, compare

``make mlp`` runs ``workloads/demo.py``, which prints one section per stage.
Each stage is a function in that file, so a script can reuse any of them.

**Trace and specs.** ``fx`` gives the graph with shapes. Each ``nn.Linear``
becomes one GEMM spec, and the ReLU that follows it becomes that spec's
epilogue:

.. literalinclude:: tinytpu_tutorial/baseline.txt
   :language: text
   :start-at: [2] Trace
   :end-before: [4] Compile

**Compile.** ACT lists every loop nest that tiles the GEMM onto a 4x4 array,
lowers each one to a TinyTPU program, and refuses the nests the instruction
word cannot express, giving the reason. The rest it ranks with its cost
model. The winner is then run on ``isa_ref`` (the ISA as numpy) against the
spec's einsum:

.. literalinclude:: tinytpu_tutorial/baseline.txt
   :language: text
   :start-at: [4] Compile
   :end-before: [5] The program

**The program.** ``disasm.py`` prints it using the operand names from the
ISA spec. Note the ``vrelu`` then ``mvout`` at the end: the ReLU is a pass
over the accumulator of its own, and it is what the second change removes.

.. literalinclude:: tinytpu_tutorial/baseline.txt
   :language: text
   :start-at: [5] The program
   :end-before: [6] Build

**Run it on the design.** ``df.build(tinytpu_isa, target="simulator")``
builds the eight-unit dataflow design from ``ip/`` (about 5 s). Each layer's
program runs on it with the real weights in DRAM, and each layer's output
becomes the next layer's input:

.. literalinclude:: tinytpu_tutorial/baseline.txt
   :language: text
   :start-at: [7] Run

Two checks are made here, and they catch different faults. The design
against ``isa_ref``, over the whole 4096-byte ``C`` buffer, catches the
hardware. The model's output against PyTorch catches the compiler and the
flow. Most output bytes are saturated at 127 or -128, because weights and
inputs in [-8, 8) summed over K=32 overflow int8. So the row comparison is
weak evidence on its own, and the per-layer full-buffer check is the strong
one.

.. code-block:: bash

    make mlp MODEL=mlp_deep TOP=5     # four layers, five mappings each
    make mlp-compile                  # stop after ACT; no design build

**A model the machine cannot run** is refused with the reason, not
approximated:

Change 1: a larger array
========================

The design's parameters live in ``ip/params.py``:

.. literalinclude:: ../../../examples/tinytpu/ip/params.py
   :language: python
   :start-at: class TpuParams
   :end-before: def __post_init__

``T`` is the array dimension, and the only parameter that changes the
*shape* of the design: ``T*T`` processing elements and ``T``- and
``T*T``-wide stream arrays. Every size is derived from it. The shipped build
reads ``TPU_T`` from the environment, so the change is:

.. code-block:: bash

    TPU_T=8 make mlp          # an 8x8 array; ~25 s, the design is 4x larger

ACT searches again and finds different tilings, with half the loop trips:

.. literalinclude:: tinytpu_tutorial/t8.txt
   :language: text
   :start-at: [5] The program
   :end-before: [6] Build

The design is still bit-exact, and the model still matches PyTorch:

.. literalinclude:: tinytpu_tutorial/t8.txt
   :language: text
   :start-at: [✓]

against the ``T=4`` build's estimate:

.. literalinclude:: tinytpu_tutorial/baseline.txt
   :language: text
   :start-at: Summary

The cost model is fitted to measurements at ``T=4``, so the near-halving is
its extrapolation, not a measurement. ``TPU_T=8 make mlp-cosim MODEL=mlp_small``
measures it (Vitis, minutes).

.. note::

   To change the *shipped* default rather than one run, edit it in both
   ``isa_spec.json`` (the ``T`` parameter) and ``microarch_isa.py``, then
   ``python gen_isa.py --write``. Editing only ``microarch_isa.py`` fails:
   ``isa_encoding.py``, which ``isa_ref`` reads, is generated from the spec
   and keeps modelling a 4x4 machine, and ``gen_isa.py --check`` reports
   "the reference model would be modelling a different machine". The two
   defaults are kept apart on purpose, so the design is checked against an
   ISA that was written down independently of it.


Change 2: a fused instruction
=============================

The ``vrelu`` and ``mvout`` at the end of every ReLU layer are two passes
over the accumulator rows. ``mvout`` already clips each lane to int8 on its
way out, so it can apply the ReLU in the same step: ``mvoutrelu``. The change
is four patches in ``tutorial/mvoutrelu/``, in the order a designer would
write them:

.. code-block:: bash

    git apply tutorial/mvoutrelu/*.patch
    python gen_isa.py --write
    make mlp

Step 1: declare it in the ISA
-----------------------------

One entry in ``isa_spec.json``: an opcode number, the operand fields (the
same as ``mvout``'s) and its **actions**, the per-unit steps that say what
the instruction does. Compared with ``mvout`` it adds one ``max0`` before
the clip:

.. literalinclude:: ../../../examples/tinytpu/tutorial/mvoutrelu/1-isa.patch
   :language: diff

``python gen_isa.py --write`` then regenerates the encoder, the decoder, the
reference model's meaning for the instruction and the ISA reference page,
none of which is edited by hand:

.. literalinclude:: tinytpu_tutorial/gen_isa.txt
   :language: text

Step 2: build it in the hardware
--------------------------------

Three Allo units change. The opcode constant goes in ``ip/isa.py``. The
accumulator (``ip/units/accumulator.py``, an Allo ``@df.kernel``) reads the
source row from ``f0`` as ``mvout`` does, and rectifies in the step that
already clips. The sequencer sends the instruction to the same two units as
``mvout``. ``dma_st`` only gets a comment, because it receives rows that
``accu`` has already rectified.

.. literalinclude:: ../../../examples/tinytpu/tutorial/mvoutrelu/2-hardware.patch
   :language: diff

Step 3: teach the toolchain
---------------------------

The assembler checks the new instruction's accumulator reads and adds its
rows to the per-unit work counts in the program header. The program DSL gets
an ``mvoutrelu()`` method, and the stress fuzzer mixes it into its random
programs half the time:

.. literalinclude:: ../../../examples/tinytpu/tutorial/mvoutrelu/3-toolchain.patch
   :language: diff

Step 4: let the compiler use it
-------------------------------

ACT's cost model gets the opcode, with the same unit loads as ``mvout``. The
lowering gets one rule: if a layer's epilogue ends in an op the retiring
instruction can apply (``FUSED_RETIRE``), fold it into the retire. Nothing
else in ACT changes. The mapspace search, ranking and checks are the same:

.. literalinclude:: ../../../examples/tinytpu/tutorial/mvoutrelu/4-compiler.patch
   :language: diff

Check it
--------

``make mlp`` is one model. Two gates check the instruction itself, and both
passed on this change:

.. code-block:: bash

    python gen_isa.py --check    # the spec, generated files and 9 consumers agree
    python stress_isa.py         # ~3 min: 640 programs on the design vs isa_ref

Both earned their keep while the change was written. The first version
failed each of them:

* ``gen_isa.py --check`` failed twice. The accumulator's clip no longer read
  as a literal saturation at -128, which is how the check verifies it. And
  ``dma_st``, now reached by two opcodes, looked like it should decode them.
  It shouldn't: both do the same thing there. That second failure was a gap
  in the check, which now lets a unit skip decoding when every opcode that
  reaches it has identical actions.
* ``stress_isa.py`` deadlocked in ``kpn_model``, a channel-level model of the
  design that had its own hand-written "only ``mvout`` sends a row to
  ``dma_st``". That rule is now derived from the spec's actions.
* ``stress_isa.py`` then found a real hardware bug: the accumulator read the
  source row from ``f1``, the DRAM-row field, instead of ``f0``. ``make mlp``
  had passed anyway, because in its programs both fields are 0. Only the
  random programs exposed it. That is the line
  ``if op == OP_MVOUTRELU: read_row = f0 + row`` in step 2.

The first two fixes are part of the tree, so the patches above are just
the designer's change.

Undo it:

.. code-block:: bash

    git apply -R tutorial/mvoutrelu/*.patch
    python gen_isa.py --write


What is and is not established
==============================

* **Cycles on this page are estimates** from ACT's cost model, fitted to
  cosim at ``T=4``. The fused instruction has **not** been through RTL cosim,
  and the ``T=8`` figure is an extrapolation. ``make mlp-cosim
  MODEL=mlp_small`` measures either one (Vitis, one ``csynth``, minutes).
* **The fused instruction is not on** ``main``. With the patches applied, the
  ``gemm.relu`` cases in ``tests/act/test_tinytpu.py`` fail, and should: they
  pin ReLU layers to the shipped ``vrelu; mvout`` programs, which cosim has
  measured. Merging ``mvoutrelu`` means measuring the new programs with
  ``TPU_TB=stress`` cosim and re-pinning those tests.
* **Untested combination:** ``TPU_T=8`` with the patches applied.


Reproducing this page
=====================

.. code-block:: bash

    make tutorial-outputs                    # re-runs everything above, ~1 min
    pytest tests/act/test_tutorial.py        # from the repo root, seconds

``make tutorial-outputs`` runs ``tutorial/capture.sh``, which writes the
outputs this page includes to ``docs/source/designs/tinytpu_tutorial/``. It
applies the patches for the last run and reverts them however it exits. The
test checks that the walk-through still compiles and matches PyTorch, that
``mlp_bias`` is still refused, and that the four patches still apply to the
tree. If a file the patches edit moves on, that test fails first.
