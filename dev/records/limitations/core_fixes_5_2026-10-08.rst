1. D-6: the server was read-first; the writer and reader saw rows one edge apart
================================================================================

**The finding as filed.** Track D's amended ``fetch:iram`` form
(``forms/fetch_d12_packed.py``, ``U4D_BODY=amended``) matched MiniTPU on
24,971 of 25,002 slots at shift 4. The 31 that differed were all
``bundle_data``, all in the first cycles after a reset, and they were exactly
the slots a write-first IRAM would get wrong. D-6 put the cause in the
``registers`` server: "the server's pipeline samples the storage one c-step
after the address". The task here was to make the server honour
``visible=1``.

**What the RTL shows** (``scripts/probe_fd12.py``: track D's own
``u4d_check`` driver, built with ``--public-flat-rw``, printing the server's
pins every cycle; track D's project ``scratch/u4d/fd12a_3p33.prj``, unchanged):

* **The server is read-first.** ``iram_mem_0_run`` registers
  ``v233 <= MUX(mem flops, v232)``, and ``iram_mem_0_wr`` writes the flops at
  the same edge. On every cycle where the write pins and the read address
  name the same row, the next ``q`` is the **old** word: 3 of 3
  (``logs/d6/probe_trackd_fd12a_collisions.txt``).
* **The writer was one row ahead of the reader.** In cycle 955 the loader's
  write pins carry trace row 953 (``we=1, wa=0, wd=…cc41afe7``, the first
  write after a reset). The fetch queue's ``c_rst`` Wire still carries row
  952, which is in reset. One cycle later the queue leaves reset and reads
  word 0, after that word was written: the new word
  (``logs/d6/probe_trackd_fd12a_cycles_950_962.txt``). The driver's per-input
  row counters agree on all 3,803 rows: ``src`` accepts ``xwe``/``xwa``/``xwd``
  one row ahead of ``xrst``/``xpause``/``xflush``/``xraddr``/``xpop``
  (``logs/d6/probe_trackd_fd12a_src_rows.txt``).
* **Why: Catapult's schedule of ``src``.** ``src`` (the form's stimulus
  adapter: array ports in, ``Wire`` channels out) pops each port and puts the
  value to a ``Wire``, interleaved. Its pipelined loop was 2 c-steps, with
  ``v1``/``v2``/``v3.Pop()`` in c-step 0 and ``v0``, ``v4``-``v7`` in c-step 1
  (track D's own ``latency.json``, ``io``). Each ``sc_out`` write followed its
  pop. So the loader's three Wires were registered one edge before the
  queue's five. A writer that runs one row ahead of the reader is a
  write-first memory on every same-row collision, and on nothing else. That
  is why the write-first reference explained 31 of 31.

So D-6 is not a server bug. It is a lowering gap in the SystemC flow: in a
kernel that is not Wire-only, one iteration's ``Wire`` outputs were not
published on one edge. Any Wire-linked composite fed by such a kernel is
exposed, whatever memory it holds.

**Confirming experiment** (``scripts/fetch_d12_packed_popsfirst.diff``: the
form's ``src`` with all eight pops first, then all eight puts; same flags,
``catapult/fd12a_popsfirst``): ``src``'s loop becomes 1 c-step with all eight
pops in c-step 0, and the form matches at shift 3:
**UNIT-MATCH 25,008/25,008, cycle for cycle, 0 stalls**.

**Change** (``mlir/lib/Translation/EmitSystemC.cpp``: ``planWireDefer``,
``emitWirePut``, ``emitAffineYield``, ``emitAffineFor``). A kernel that is
not Wire-only (a ``Stream``, channel or array port, or a stream/channel op),
whose ``Wire`` puts (comb outputs excluded) all sit in one top-level loop,
gets the following:

* one shadow per Wire it writes (``__wput_<port>``, starting at the port's
  reset value 0), declared before the loop;
* each put assigns the shadow;
* at the end of every iteration (the loop's ``affine.yield``), after the
  iteration's last handshake, each shadow is written to its port once.

A Wire that is not written in an iteration keeps its value, as a register
does. A kernel with puts outside one iteration loop is emitted as before.
Wire-only kernels (one iteration is one edge already), the D-12 servers and
owners among them, are unchanged. The rule is written in
``docs/source/backends/systemc.rst`` (after the link table).

The emitted ``src`` of the form, before and after
(``logs/d6/fd12a_src_0_emission.diff``): eight ``vN.write(x)`` become
``__wput_vN = x``, and eight ``vN.write(__wput_vN)`` follow the last pop.
Nothing else in the design changes. (The other differences from track D's
``kernel.cpp`` come from core-fixes-4, which is on ``u1-pilot`` and was not
on track D's base: S-2's port order and the ``allo unreset process`` marker.)

**Track D's command, re-run** (``U4D_BODY=amended u4d_run.sh fd12a_3p33 fetch
form:fetch_d12_packed --inst iram --clock 3.33 --pipeline-all
--unroll-nested``, the form unchanged; ``catapult/fd12a_3p33``, 81 s, 893 MB):

**Draft upstream issue text** (cornell-zhang/allo: the SystemC emitter is

   *Title:* SystemC: a kernel with stream/array ports writes one iteration's
   ``Wire`` outputs on different clock edges

   In a kernel that is not Wire-only (it pops array or stream ports), Catapult
   2024.2 may pipeline the loop over several c-steps and place each ``sc_out``
   write in the c-step of the handshake read before it. A stimulus kernel
   that pops 8 array ports and puts each to a ``Wire``, interleaved, ran 2
   c-steps: 3 Wires were registered one edge before the other 5. Downstream,
   two owners of one D-12 memory then saw rows one edge apart, and every
   same-row read returned the word being written (a write-first memory,
   though the server is read-first on the RTL). The fix publishes each
   iteration's Wire outputs together, from shadows, after the iteration's
   last handshake: the loop is 1 c-step and a 25,008-slot trace matches the
   reference RTL cycle for cycle.

2. E-F1: an untyped integer literal was always ``int32``
========================================================

**Before.** ``TypeInferer.visit_Constant`` typed every int literal ``int32``,
and a global int too (``visit_Name``). ``shift_rule(Int32, Int32)`` is
``Int32``, so a literal expression was computed at 32 bits, and the builder
materialised every untyped constant as ``i32``. Measured on the bindings of
this branch, at commit 1, with HEAD's Python (``logs/ef1/pretest_results.txt``:
``tests/test_wide_literal.py`` run one test per process against that tree):

* every wide case gave a wrong value, silently: ``x | (1 << 35)`` was ``x``;
  ``x + (1 << 40)``, ``x + 1099511627776`` and ``x | BIG`` (a global
  ``1 << 40``) all dropped the 2**40;
* ``x + 0x80000000`` and ``x & 0xFFFFFFFF`` on a ``UInt(64)`` sign-extended
  the 32-bit pattern;
* ``y: UInt(64) = 1 << k`` with ``k = 35`` was 0;
* ``x >= (1 << 35)`` **segfaulted** the ``llvm`` build, and
  ``(x & (1 << k)) == (1 << k)`` did not finish in 120 s;
* ``Int(64)`` gave the same wrong values;
* the limits repro printed ``REPRODUCES``.

**Change** (``allo/ir/infer.py``, the ``E-F1`` block and its calls in
``visit_Constant``, ``visit_Name``, ``visit_UnaryOp``, ``visit_BinOp``,
``visit_Compare``, ``visit_AugAssign``, ``visit_Assign``,
``visit_AnnAssign``; ``allo/ir/builder.py``, ``build_folded_literal`` called
from ``build_Constant``, ``build_Name``, ``build_UnaryOp``, ``build_BinOp``).
Rules 1-3 below are chosen so that **a literal whose value is a 32-bit
pattern keeps today's typing next to operands of at most 32 bits**:

1. **Fold.** A literal expression is int literals and global ints (not
   shadowed by a local) under ``+ - * << >> | & ^`` and unary ``- + ~``
   (``/``, ``//``, ``%``, ``**`` excluded: their Allo semantics differ from
   Python's). It is evaluated in Python. If its value lies outside
   ``[-2**31, 2**32)`` it becomes one ``arith.constant`` of its minimal
   width: ``UInt(n)`` for a non-negative value, ``Int(n + 1)`` for a negative
   one.
2. **Context.** Next to an integer operand wider than 32 bits (``| & ^ + -
   *``, the comparisons, augmented assignment), or as the value of such a
   target, two kinds of literal take that operand's type: a literal in
   ``[2**31, 2**32)``, and the literal on the left of a shift by a
   non-constant amount. This reaches inside an expression of literals, so in
   ``x & ((1 << k) - 1)`` the shift under the ``-`` takes the type too (the
   pattern in ``template/sequencer.py``).
3. **Refuse.** A folded literal stored into an integer variable, array
   element or target that it does not fit is refused, naming the expression
   (``integer literal `1 << 70` = … does not fit `y` of type ui64``). This
   includes ``y: uint32 = 1 << 35``, which was silently 0 or poison before.
   ``customize`` reports it and exits, as it does every front-end error
   (limitations item C).

**The one narrow-source change, judged intended.** Allo types ``int32 ±
int32`` as ``Int(33)``. Next to that, ``0xFFFFFFFF`` now takes rule 2: it is
the number 4,294,967,295 (``arith.constant 4294967295 : i33``), not ``-1``
sign-extended. The int32 result is unchanged bit for bit (a truncation
follows). A result kept wider than 32 bits is the masked value, which is what
the source says; before, it was E-F1's sign-extension
(``test_pattern_literal_next_to_int33``).

**Narrow code unchanged** (``logs/ef1/narrow_ir/``): ten kernels, the same
IR text before and after the change. They cover:

* shifts, ``|`` ``^``, masks ``0xFFFFFFFF`` / ``0x80000000`` / ``1 << 31`` on
  ``uint32``, and ``== 0xFFFFFFFF`` on ``int32``;
* ``uint8 + 300``, ``int8 & -2``, global ints, index arithmetic, ``1 << k``
  on ``int32``, and ``|=`` / ``+=`` on ``uint16``;
* small literals next to a ``UInt(64)``.

``test_narrow_ir_unchanged`` holds one such kernel's arith lines against the
pre-change text. TinyTPU's emission hashes are unchanged (section 3).

4. Draft upstream issue text (E-F1; not filed)
==============================================

D-6's draft is in section 1 (fork-only: the SystemC emitter is the fork's).
E-F1 is upstream-relevant: the same text compiles the same way in upstream
Allo's front end (and in AMC's vendored Allo, track E's E-A4).

   *Title:* Untyped integer literals are always ``int32``:
   ``x | (1 << 35)`` on a 64-bit value silently loses the bit

   ``TypeInferer.visit_Constant`` types every integer literal ``int32``, and
   ``shift_rule(int32, int32)`` is ``int32``. So a literal expression is
   computed at 32 bits, whatever it is combined with:

   .. code-block:: python

      def k(A: uint32[2], O: uint32[2]):
          for i in range(2):
              x: UInt(64) = A[i]
              y: UInt(64) = x | (1 << 35)   # bit 35 stays clear
              O[i] = y[32:64]               # [0, 0], want [8, 8]

   The same happens to ``x + (1 << 40)``, to a lone ``1099511627776``, to a
   global ``BIG = 1 << 40``, to ``y: UInt(64) = 1 << k`` with ``k >= 32``,
   and to ``x + 0x80000000`` (sign-extended). There is no warning. One form,
   ``x >= (1 << 35)``, segfaults the LLVM build. Proposal (implemented on
   the fork, ``sunwookim028/allo`` branch ``core-fixes-5``):

   1. fold a literal expression (literals and global ints under ``+ - * <<
      >> | & ^``, unary ``- + ~``) whose value is not a 32-bit pattern to one
      constant of its minimal width;
   2. next to an operand or target wider than 32 bits, type a literal in
      ``[2**31, 2**32)`` and the literal left of a shift by a variable
      amount as that operand;
   3. refuse a folded literal stored into an integer it does not fit, naming
      the expression.

   Literals that are 32-bit patterns next to operands of at most 32 bits keep
   today's typing, so existing narrow code builds identical IR. One
   deliberate exception: ``0xFFFFFFFF`` next to the 33-bit sum of two
   ``int32`` is 4294967295, no longer ``-1``; the int32 result is the same.
   Evidence: 18 wide cases wrong or crashing before and right after, the
   narrow IR identical on ten kernels, and 928 other tests with unchanged
   outcomes.
