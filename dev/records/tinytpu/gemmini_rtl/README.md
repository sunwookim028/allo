# Gemmini's accelerator, for the same DC flow ours goes through

`rtl_handoff/` hands zhang-21 our design; this hands it the opponent, so the
Gemmini comparison has an area axis and not only a cycle axis. Both sides:
Design Compiler `W-2024.09`, FreePDK45 `view-standard`, 3.33 ns, topographical,
flatten effort 3, `sram_mode='none'`, mflowgen 0.8.0 at `aee0e5d6`.

| directory | Chisel config | against |
| --- | --- | --- |
| `DIM4_int8_capmatched/` | `Int8Dim4AreaGemminiRocketConfig` | `rtl_handoff/T4_MAXDIM16_shipped_baseline` (1,136,598) |
| `DIM8_int8_capmatched/` | `Int8Dim8AreaGemminiRocketConfig` | `rtl_handoff/T8_MAXDIM64` (2,481,926) |

Each directory holds the flat RTL, `MANIFEST.json`, a README arguing its own
boundary, and **two** file lists. Generated by `export_gemmini_rtl.py`; do not
hand-edit.

## The three things that make or break the comparison

**The unit is `Gemmini`, not the SoC.** Chipyard elaborates Rocket, an L1, an
L2, the buses and a DRAM model around the accelerator; we have none of that.
The export is the transitive closure of the module instantiation graph from
`Gemmini` -- 138 modules at DIM=4, 136 at DIM=8 -- computed from the elaborated
RTL rather than picked by hand, so the boundary is checkable. Gemmini's own
4-entry TLB is inside that boundary and we have no translation at all; it is the
one arguable cut, and it is reported rather than resolved (`report_area
-hierarchy` on `FrontendTLB`).

**The memories are capacity-matched, because the memory treatment would
otherwise be the whole measurement.** Stock Gemmini carries 256 KiB of
scratchpad and 64 KiB of accumulator; as flip-flops that is 2,621,440
registers, against 200,561 sequential cells in our entire T=4 design. These
configs carry 8 KiB and 4 KiB -- 98,304 bits. The shrink is **cycle-neutral**:
`tiled_matmul_auto` issues exactly one `loop_ws` at every published shape from
256/64 KB down to 4/4 KB, so no Gemmini cycle number moves. It stops being
neutral at 32x32x32.

How well 12 KiB matches, measured out of the RTL on both sides (every
`*_RAM_*` module's depth x width x hierarchical instance count):

| our variant | operand + accumulator | all memory modules | vs Gemmini's 12 KiB |
| --- | --- | --- | --- |
| `T4_MAXDIM16_shipped_baseline` | 2.5 KiB | 3.50 KiB | Gemmini has **4.8x** |
| `T4_MAXDIM64_shipped` | 10.1 KiB | 18.62 KiB | Gemmini has 1.19x |
| `T8_MAXDIM64` | 12.25 KiB | 20.75 KiB | **matched to 2 %** |

The "4 KiB scratchpad, 4 KiB of vector registers, 2.1 KiB accumulator" this
project quotes for itself is the **`MAXDIM=64`** build; at `MAXDIM=16` both
arrays are 64 rows of 32 bits, 256 bytes apiece.

**So two numbers come out, not one, and the logic-only one is the headline.**
`sv2v_manifest.f` includes the memory arrays; `sv2v_manifest_nomem.f` omits the
four `*_ext` modules, so `mem` and `mem_0` elaborate as empty black boxes and DC
reports the accelerator's logic alone. That figure is invariant to both the
memory treatment and the capacity choice -- provided our side omits its
`*_RAM_*` modules in the same way, which is a second run on our side.

## What is different from the Vitis handoff

- **sv2v is required here.** firtool 1.75.0 emits packed multidimensional
  arrays and assignment patterns outside any `ifdef`, so this is SystemVerilog,
  not Verilog-2001, and the files are named `.sv` accordingly. Set
  `normalize_rtl: True`, or read with `analyze -format sverilog`.
- **`SYNTHESIS` must be defined** at read time, or `plusarg_reader` arrives as
  `$value$plusargs` in an `initial` block.
- **The top-module check is not a problem**: `module Gemmini(` carries a
  comment, not an attribute.
- **`design_path` is this directory**, not a `rtl/` subdirectory inside it --
  the same flat layout as `rtl_handoff/`.

## Reproducing the elaboration

`~/chipyard` is shared and mostly read-only. Two config files are ours
(`gemmini/chipyard_RoCCAcceleratorConfigs.patch`,
`gemmini/gemmini_CustomConfigs.patch`); nothing else is touched.

```bash
cd ~/chipyard && source env.sh          # replaces the allo conda env: separate shell
cd sims/verilator
make verilog CONFIG=Int8Dim4AreaGemminiRocketConfig -j16   # ~2 min, ~0.5 GB
make verilog CONFIG=Int8Dim8AreaGemminiRocketConfig -j16
cp <repo>/examples/tinytpu/gemmini/gemmini_params.dim4.h \
   ~/chipyard/generators/gemmini/software/gemmini-rocc-tests/include/gemmini_params.h
```

That last line matters: **every elaboration rewrites `gemmini_params.h` in
place**, so a C build after one silently targets the wrong hardware. The
exporter does not trust the header at all -- it reads `DIM` back out of the
scratchpad's own geometry in `.top.mems.conf` -- but the benchmark build does.

```bash
python examples/tinytpu/export_gemmini_rtl.py
```

The export refuses a named top module that nothing defines, an empty resource
record, and a memory footprint over 32 KiB -- the same two guards
`export_rtl.py` makes, plus the one this comparison specifically needs.
