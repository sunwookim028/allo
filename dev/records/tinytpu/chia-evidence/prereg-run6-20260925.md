## Why this run, and why it can only happen now

The instruction set used to be frozen, because `isa_ref.py` is what the stress
gate compares random programs against and a candidate that rewrites its own
reference model can weaken the rule and score strictly better. Three things
replaced the freeze, and none is a file the candidate can reach:

* **`run.py --verify`, the PyTorch oracle, is a gate and runs first** —
  `torch.nn.Linear`'s own forward on the model's real weights, bit-exact,
  with nothing a candidate writes on either side. **2.9 s.**
* **`gen_isa.py --conform` is a gate on the candidate's own spec** — frozen,
  and it holds the spec, the generated encoding, the design's bit slices, the
  assembler, the reference model and the emitted HLS to each other. **34.9 s.**
* **The GEMM goldens were never `isa_ref`.**

So an ISA change is now checkable, and the check that matters most is the
cheap one. Run 2 is why that ordering is load-bearing: an arm widened the
encodable mapspace from 3 nests to **17**, and **10 of the 17 computed the
wrong answer**, including the nest the frozen mapper itself picked. Breadth
over a design space with no cheap external oracle manufactures wrong machines.
This run is breadth over the *one* space where a candidate can rewrite the
rulebook, and it is defensible only because the external oracle is 2.9 s.

## The question

> Given the instruction set in `EDITABLE` and a breadth phase on the fast
> tier, can a candidate author a **coherent instruction-set change** — a
> modified `isa_spec.json`, its regenerated `isa_encoding.py`, an `isa_ref.py`
> that describes the new behaviour, and the unit and assembler changes that
> implement it — that reaches **`gate:isa` and `gate:pytorch` clean**? And of
> those that do, does any reach a graded verdict that beats the run's own
> measured control?

Two bars, deliberately separated. The first is *coherence*: the candidate
produced an instruction set that is internally consistent and that computes
the right answer. The second is *value*: it was also faster. Every previous
run collapsed these, because every previous run changed a knob where
coherence was free.

**Why the null is informative.** Nobody knows where ISA candidates die,
because none has ever been made. The verdict names the stage, and each stage
is a different repair:

| dies at | what it means | what it costs to fix |
| --- | --- | --- |
| `gate:isa` | the five artefacts drifted; `regenerate_isa` was not used, or the reference imported an opcode number from the design (`check_reference` forbids it) | tool discoverability and prompt |
| `gate:pytorch` | the candidate can *encode* a new instruction but the machine no longer computes | a real design failure, and the oracle earning its place |
| `gate:stress` | right on the corpus, wrong at the edges — 492 runs, full-range int8, corners, boundaries | a corpus finding, not a prompt one |
| `gate:param` | the change only exists at the scored configuration | the candidate hard-coded, as run 1's winner did with `T = 4` |
| nothing proposes a spec edit at all | the surface is unreachable in practice | the prompt and the spec listing, not the model |

That last row is the cheapest and most likely finding, and it would be worth
the run on its own: five runs have had these paths editable and none used
them.

## The prediction, and what would falsify it

- **At least one candidate reaches a graded verdict carrying a non-empty
  `isa_spec.json` diff.** With two workers, two iterations and a breadth phase
  that must produce twelve variants each, a spec edit somewhere is likely.
  **Falsified by zero spec diffs reaching a verdict** — which would make "the
  surface is unreachable in practice" the run's headline.
- **No ISA change wins.** I predict `not-better` for every spec-modifying
  candidate. The burst is the cheapest legal win in the tree and an opcode is
  one of the dearest; a new instruction has to pay for its own decode, its own
  encoding pressure and its own unit logic before it saves a cycle.
  **Falsified by an `accept.py`-confirmed win whose diff includes
  `isa_spec.json`** — which would be the series' **first novel design point**.
- **The modal death is `gate:isa`, not `gate:pytorch`.** Weakly held. A spec
  edit has five artefacts to keep in agreement and only one of them —
  `isa_encoding.py` — is written by a tool. **Falsified by the stage
  histogram**, and I expect to be told I am wrong here in the same way run 4's
  "no win" was wrong: the reasoning may survive the verdict.
- **The most common *kind* of spec edit is an encoding-only change** — a
  widened immediate, a repurposed reserved field, a fused form of two existing
  instructions — rather than a new unit behaviour. **Falsified by the diffs.**
  This is not itself a negative: an encoding-only change that wins is still a
  change to the instruction set and still qualifies.
- **Spend under $25.** Four latency-bound sessions at $4-5. **Falsified by the
  database figure**, never by `usage`.

## What counts as a novel design point, for this question

The series definition, unchanged: *a candidate-authored change to a unit, the
wiring or the instruction set, that beats the run's own measured control, and
is not a knob already in the tree.* An ISA change that wins satisfies it by
construction — the instruction set is named in the definition, and there is no
opcode in the tree to rediscover.

**This is the run in the series that can produce one.** It is also the run
where the definition has to be read strictly in the other direction: a
spec diff that *only* renames fields, reorders bits or adjusts a default
expression, and wins because of a parameter that moved alongside it, is a knob
flip wearing an ISA diff. The report attributes the win — as run 3 did, with a
$0 follow-up that showed the burst widening was worth the entire -129 and the
channel depth zero — before it calls anything novel.

## What counts as a negative, and is reported as a result

- **Zero spec diffs.** The headline finding, with the trace showing whether
  `read_spec` was ever called on `isa_spec.json`.
- **Spec diffs that all die at one stage.** A stage histogram is a map of the
  surface, and this run is the first thing that could draw one.
- **A candidate that passes `gate:isa` and fails `gate:pytorch`.** The oracle
  refusing an ISA change is the single most valuable negative available here:
  it is the check that exists *because* the ISA is editable, and it has never
  been observed doing its job against a real ISA edit.
- **A win `accept.py` refuses** on a clean worktree with its own bindings: the
  search is producing plausible-but-wrong candidates.
- **The cross-check firing.** A stop, not a datum.

## Rediscovery register — a win that is any of these is not a finding

1. **`TPU_DMA_WIDEN` / `_WIDEN` defaulting on**, including any spec-side
   `default_expression` that achieves the same widening. Run 4's entire diff
   was this plus its regenerated encoding, so **a spec diff is not by itself
   evidence of novelty** and this run must check for exactly that disguise.
2. **The `ac2sp` channel depth** (`ip/tinytpu.py`, `QD` -> 32).
3. **`QD` itself.**
4. **A new opcode that no program the evaluator runs ever executes.** Not a
   rediscovery — a no-op. If cycles move, the cause is elsewhere and the
   report finds it before crediting the opcode.

Kept in this file, **not in the prompt**.

## Stop rules

1. **The cumulative or per-run cap refuses.** The ceiling is not raised.
2. **The control disagrees with the published row.** A stop, and a person
   decides.
3. **`smoke.py` fails.**
4. **A `tamper` verdict on a tree that should have been clean.**
5. **Run 5 reported fewer than eight variants in an iteration.** Then breadth
   is not affordable, this run's Phase A rule is unachievable, and it must be
   re-planned as a depth run before it is signed off.
6. **Both workers reach iteration 2 with zero spec diffs.** The question is
   answered — the surface is unreachable — and a third iteration buys a
   repetition, not a datum.

## Deviation reporting

Any departure from the plan above — a different worker or iteration count, a
different cap, a restart after a kill, a hand-edited spec, a second
`smoke.py`, a changed phase rule, an objective that moved under the run, or a
question changed after the first call — is named in the appended result
section with what it was and why. There is no resume: a restart is a new run,
a new run directory and a new index row. If the plan is departed from before
any paid call, this page is edited and re-pushed to `main` instead, and that
edit is itself noted.
