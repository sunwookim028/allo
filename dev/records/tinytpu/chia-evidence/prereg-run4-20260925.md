## Why a run at all, and why the smallest one

The whole paid path has been unexercised since run 3. The resumability work
made **no cloud call**: `gcp_setup.sh`, `preflight.py`'s gcloud reads,
`smoke.py` and the caps firing had never been run. Everything in that list
**except `smoke.py`** was exercised at $0 on 2026-09-25 and is recorded in
`dev/records/tinytpu/chia-evidence/paid-path-dry-20260925.md`. What is left is
exactly the part that cannot be had for free: **one real Vertex call, and a
worker iteration that a real model drives.**

So this run is sized to prove the path, not to search. **One worker, one
iteration.** At n=1 a win would be one win and no rate of discovery, which
every CHIA prereg has said; at one iteration that is doubly true, and this page
does not ask for one.

## The question

**Primary (recommended).**

> On `main` as it ships today (175 / 265 / 421 / 482 / 674), does one worker
> doing one iteration against the current `EDITABLE` surface reach a **graded
> verdict** — `win`, `not-better` or `rejected` — carrying a nonce-vouched
> cosim cycle count at both scored shapes, with the run's own measured control
> recorded beside it?

A null result here is informative, which is why this is the question: a run
that does **not** reach a graded verdict names the stage it died at
(`setup`, `policy`, `import`, `invariant`, `tamper`, `model`, `gate`,
`score`), and that stage name is the finding. Three of the loop's historical
breaks — `MAIN_BASE`, the unclosed frozen set, `control.PUBLISHED` — each
refused *every* candidate at one named stage, and each was invisible to the $0
harness at the time. This run can only distinguish "the harness's guards pass"
from "a real model driving real MCP tools produces something the evaluator can
score", and that is the distinction $0 cannot buy.

**Alternative, if the owner would rather buy a design question** (it costs the
same and answers the primary one on the way, but it depends on the `T`/`MAXDIM`
search work landing on `main` first — another agent is doing that, and if it is
not merged, this alternative is not available and the primary stands):

> With `T` and `MAXDIM` newly searchable, does the one iteration propose a
> change to **those** parameters, or to the datapath as every previous run did?

That is descriptive at n=1 — a fact about where the agent looks when the search
surface widens — and both answers are worth having: if it ignores the new
parameters, that is a finding about the prompt and the spec listing, not about
the model.

**The owner picks one.** Running both is two runs, not one.

The published row is **not** the control: `control.crosscheck` holds it to the

a datum, and no result of the run may be reported until a person says whether
the toolchain moved or the design changed.

## The prediction, and what would falsify it

- **Primary: yes, one graded verdict.** Falsified by any death at a named
  stage. I hold this only weakly: run 3 graded six of six, but the design has
  since changed and the `EDITABLE` surface with it.
- **No win.** I predict `not-better`. Run 3's two wins are *still not landed*
  (see the rediscovery register), so the headroom they found is nominally still
  there — which is exactly why a win here would most likely be a rediscovery
  rather than a finding. Falsified by an `accept.py`-confirmed win that is not
  on the register below.
- **Spend under $8.** A worker-iteration has cost $2.79–$4.76 over runs 1 and
  3; one iteration plus one baseline evaluation should not pass $8. Falsified
  by the database figure (`spend.py run <run>`), never by `usage`.

## What counts as a negative, and is reported as a result

- **Zero candidates graded**, with the stage named. A result about the repair.
- **A win `accept.py` refuses** on a clean worktree with its own bindings: the
  search is producing plausible-but-wrong candidates. A result about the gate
  ladder.
- **The cross-check firing.** A stop, not a datum.
- **A `tamper` verdict on a tree that should have been clean** is, in practice,
  another agent editing the checkout mid-measurement (guard 4). Suspect that
  before the candidate — and note that a second agent is working in
  `chia_agent/` this week, which makes it likelier than usual here.
- **`smoke.py` failing.** Then the paid path is *not* proven and the run stops
  there, having cost cents. That is the cheapest possible negative and it is
  the one this run is really buying.

## Rediscovery register — a win that is any of these is not a finding

1. **`TPU_DMA_WIDEN`.** Already in `microarch_isa.py`
   (`_WIDEN = TpuParams.widest_burst(T, MAXDIM) if os.environ.get("TPU_DMA_WIDEN") == "1" else 1`),
   **off by default**, and the agent cannot switch it on through the
   environment because every `TPU_*` variable is scrubbed before cosim — so it
   would change the default, exactly as run 3's winner did.
2. **The `ac2sp` channel depth.** `ip/tinytpu.py` still declares it at `QD`;
   run 3's winner deepened it to 32.
3. **`QD` itself.** `QD=16` landed at `63ee6ec7` and is the reason the
   published row moved to 175 / 265 / 421 / 482 / 674. A candidate that raises
   it again is walking a path already walked.

Items 1 and 2 together **are** run 3's accepted win, at 175 / 265 / 386 / 435 /
627. It was accepted and never landed. If run 4 produces that diff again it has
rediscovered a result this repository already holds, and the report says so in
those words.

## Deviation reporting

Any departure from the plan above — a different worker or iteration count, a
different cap, a restart after a kill, a hand-edited spec, a second `smoke.py`,
an interrupted run resumed by hand (there is no resume; a restart is a new
run and gets a new run directory and a new row), or a question changed after
the first call — is named in the appended result section with what it was and
why. A deviation that is not written down makes the whole page retrospective,
which is the one thing a pre-registration cannot survive. If the plan is
departed from before any paid call, this page is edited and re-pushed to `main`
instead, and that edit is itself noted.
