## What changed since run 4

Two things, and the run exists because of the first.

1. **The oracle is tiered.** A fast functional tier is callable freely, a
   slower gate tier sits behind it, and `score_cycles` is capped per
   iteration. Until now every legality question cost 74 s (`run_functional
   _check`, called 4-7 times a session against a docstring that claims 15 s)
   and every objective question cost 352 s, so a session bought two probes.
2. **Sessions are traced per turn** (`session_trace.py`), so this run can
   report what each variant touched and what it cost even when nothing wins.
   Run 3 could not: five of its six iterations timed out with an empty
   `agent_summary`, and the search had no memory.

## The question

> With the fast tier available and `score_cycles` capped, does one worker
> doing a **breadth phase** — propose a variant, check legality, record it,
> repeat, with no cycle scoring permitted — reach **twelve or more distinct
> variants in one iteration**, touching **five or more distinct `EDITABLE`
> paths**, and what does a variant actually cost in model turns, seconds and
> dollars?

Distinctness is counted from the trace by the set of `EDITABLE` paths a
variant's edits touched, and is reported whether or not the bar is met. Two
variants that edit the same single path are one path, not two; twelve
variations of the same idea would satisfy the first bar and fail the second,
and that combination is itself the most interesting negative this run can
produce.

**Why the null is informative.** The series design claims breadth is now
affordable and that a breadth null is a *map* rather than a sentence. If the
worker reaches four variants and stops, the claim is false and the trace says
which of the three assumptions broke: turns per variant (A1), the tier's cost
(A2/A4), or per-turn latency rising with context (A2). Each of those is a
different repair, and each is cheaper to learn here than inside run 6.

## The prediction, and what would falsify it

Written to be able to fail the way run 4's did — verdict wrong, reasoning kept
beside it.

- **Twelve or more variants: yes.** At the design page's central figures — 2.5
  turns a variant, 35 s a turn — a 2,400 s session is ~26 variants, so twelve
  is half the estimate and should survive a factor-of-two error. **Falsified
  by fewer than twelve distinct variants in either iteration.**
- **Five or more distinct paths: no, I predict three or four.** Runs 1, 3 and
  4 touched `ip/units/dma_load.py`, `ip/units/sequencer.py`,
  `microarch_isa.py` and `ip/tinytpu.py` and nothing else; breadth changes how
  many variants a worker proposes, and I do not believe it changes where a
  worker looks without being told to. **Falsified by five or more distinct
  paths across the phase.** This is the prediction I most expect to be wrong
  about in the *useful* direction, and it is the one to read first.
- **Per-turn latency rises above 45 s by turn 40.** Context growth, not the
  oracle, is the ceiling on breadth: `read_spec` returns 96 KB of both files
  whole and was called 12-19 times a session in run 3. **Falsified by the
  trace showing flat per-turn latency across the phase.**
- **No win, and no cycle score better than the control.** One or two capped
  scores at the end of a breadth phase is not a search. **Falsified by an
  `accept.py`-confirmed win.** If one comes back, the register below decides
  whether it is a finding.
- **Spend under $12.** A latency-bound session runs more turns than run 4's
  56, at $0.049-$0.074 a message. **Falsified by the database figure
  (`spend.py run <run>`), never by `usage`.**

This run does **not** predict what the tiering work will measure. The tier's
per-call cost is an input to be reported, not an outcome to be scored.

## What counts as a novel design point, for this question

The series definition is unchanged and is not relaxed here: *a
candidate-authored change to a unit, the wiring or the instruction set, that
beats the run's own measured control, and is not a knob already in the tree.*
**This run is not expected to produce one** — it is a shakedown with at most
two cycle scores.

What it *can* produce, and what is reported separately and explicitly **not**
called a design point: a **legal non-register variant** — a variant that
passes the fast tier, is not on the rediscovery register, and touches a path
no previous run has edited. That is a fact about where breadth looks. It is
not a result about the design, because nothing measured its cycles.

## What counts as a negative, and is reported as a result

- **Fewer than twelve variants**, with the trace's account of where the
  session's turns went. A result about the arithmetic.
- **Twelve or more variants over one or two paths.** Breadth in count and not
  in kind: a result about the prompt, and a direct instruction for run 6.
- **A high illegality rate.** If most variants fail the fast tier, report the
  stage each died at. A breadth phase that generates mostly wrong machines is
  run 2 with a cheaper filter — still worth knowing, and the filter catching
  them is the point.
- **The `score_cycles` cap not holding.** If the worker scores more than the
  cap allows, Phase A is advisory rather than enforced and runs 6 and 7 must
  be re-planned. A result about the harness.
- **The cross-check firing** (control against the published row). A stop, not
  a datum.

## Rediscovery register — a win that is any of these is not a finding

1. **`TPU_DMA_WIDEN` / `_WIDEN` defaulting on.** Run 1 found it, run 3
   rediscovered it as a named prediction, run 4 deleted its guard. Three of
   four series wins.
2. **The `ac2sp` channel depth**, `ip/tinytpu.py`, `QD` -> 32. Run 3's other
   half.
3. **`QD` itself.** Landed at `63ee6ec7`; raising it again is a walked path.
4. **Anything at all if the burst has been landed into the control before this
   run.** Then item 1 is in the baseline and a candidate re-finding it cannot
   win; if one appears to, that is a control defect and a stop.

This register stays in this file. **It is not put in the agent's prompt** —
the series design argues that naming a working win to a model rewarded for
wins makes it cheaper to find, not dearer.

## Stop rules

Stop the run, report what is in hand, and do not restart inside the same run
directory:

1. **The cumulative or per-run cap refuses.** The ceiling is not raised.
2. **The control disagrees with the published row.** A person decides whether
   the toolchain moved or the design changed before any result is reported.
3. **`smoke.py` fails.** The paid path is not proven; the run stops there
   having cost cents.
4. **A `tamper` verdict on a tree that should have been clean.** Suspect
   another agent editing the checkout mid-measurement before suspecting the
   candidate — that happened in run 4's week and it is likelier than usual
   while the tiering work is in flight.
5. **Iteration 1 produces fewer than four variants.** The shakedown has
   answered its question in the negative; a second iteration buys nothing.

## Deviation reporting

Any departure from the plan above — a different worker or iteration count, a
different cap, a restart after a kill, a hand-edited spec, a second
`smoke.py`, a changed phase rule, an objective that moved under the run, or a
question changed after the first call — is named in the appended result
section with what it was and why. There is no resume: a restart is a new run,
a new run directory and a new index row. A deviation that is not written down
makes the whole page retrospective, which is the one thing a pre-registration
cannot survive. If the plan is departed from before any paid call, this page
is edited and re-pushed to `main` instead, and that edit is itself noted.
