# Pre-registration: CHIA ISA-track run 3, 2026-09-24

Written and committed **before** the run, so that a flat result is a
measurement rather than an excuse. Nothing below is edited after the run
starts; the outcome goes in a separate section appended afterwards, and any
deviation from this plan is named there.

## What changed since run 2

The loop did not run at all on current `main`. Five pins had gone stale
(`MAIN_BASE`, `check_invariants`'s MAXDIM, `evaluate.FROZEN`'s missing ISA
spec, `control.PUBLISHED`, the per-run spend cap's scope), and the design under
search had become a **package**: the hardware left `microarch_isa.py` for eight
modules under `ip/units/`, leaving a 102-line instantiation behind. The
harness's `EDITABLE` still named two files, so what the agent could edit no
longer contained the machine. `chia_agent/design.py` now names fourteen
editable paths, and the MCP tool serves them by path.

That is the change this run is aimed at, and it is the reason the run is worth
its money: **the search surface is different from run 1's**, not merely
re-enabled.

## The question

> On the design as it ships today (175 / 265 / 421 / 482 / 674), does a
> two-worker, three-iteration search over the **decomposed** design produce
> candidates that reach a **graded verdict** — and does any of them beat the
> control the same run measures?

This is a question the ISA-track gate ladder can answer. It scores by Vitis
HLS 2023.2 C-synthesis plus xsim RTL co-simulation on the real design at
4x4x4 and 16x16x16, each testbench bit-exact, against a control measured on
the same machine, the same Vitis install and the same `mlir/` build. It is
**not** the question the abstraction track cannot see: nothing here asks
whether a new compiler capability exists, because a ladder that exercises a
compiler only through designs that already work cannot observe one in either
direction (`docs/source/extensions/chia_results.rst`). Cycles on this design
are exactly what this ladder measures.

## Primary outcome (the end-to-end bar)

**At least one candidate reaches a graded verdict** — `win`, `not-better` or
`rejected` — carrying a nonce-vouched cosim cycle count at both scored shapes,
with the run's own measured control recorded beside it.

This, and not "the harness's own tests pass", is what "the loop runs end to
end" means. `test_harness.py` is $0 and proves the guards; it does not prove
that a real model, driving real MCP tools, produces something the evaluator
can score.

## Secondary outcomes

1. **Does anything win?** Strictly fewer summed cosim cycles (4x4x4 +
   16x16x16) than the in-run control, with every gate passed: `bench_isa`
   `ALL EXACT`, `stress_isa` n/n exact, `param_check` exact at `TPU_MAXDIM=8`,
   `TPU_MAXDIM=12` and `TPU_T=8 TPU_MAXDIM=32`, both testbenches bit-exact,
   estimated clock ≤ 3.33 ns.
2. **Where do the agents edit?** Which of the fourteen paths each accepted or
   rejected candidate touches, and whether workers scope a change to one unit
   or scatter it. Descriptive at n=1 — a count, not a claim.

## What I expect

- **Primary: yes.** I expect the loop to complete its baseline evaluation and
  at least one scored candidate per worker. If it does not, the repair is
  incomplete and the run's value is the stage name where it stops.
- **Secondary 1: probably not a win.** The shipped design has already absorbed
  run 1's two wins *and* the gap-attribution stack; 16x16x16 went 686 → 674
  and 4x4x4 172 → 175, so the headroom that run 1 found is largely spent. My
  prediction is **0 or 1 accepted wins across both workers**, with
  `not-better` the most likely per-candidate verdict.
- **A predicted rediscovery.** `TPU_DMA_WIDEN` already exists in
  `microarch_isa.py` and is **off** by default; `TpuParams.widest_burst` gives
  the widest beat the 64-byte bus holds. The agent cannot switch it on through
  the environment (every `TPU_*` variable is scrubbed before cosim) but it can
  change the default. If a win arrives and it is that, it is a
  **rediscovery of a lever already in the tree**, not a new finding, and it
  must be reported as such. Recording the prediction here is what makes that
  distinction checkable afterwards rather than arguable.
- **Secondary 2:** I expect at least one worker to edit a file under
  `ip/units/`, because that is where the hardware now is and the prompt says
  to prefer one unit. If every candidate edits only `microarch_isa.py`, the
  decomposition bought navigability and nothing else, which is worth knowing.

## What counts as a negative

- **Zero candidates graded.** Every iteration dies at `setup`, `policy`,
  `import`, `invariant` or `tamper`. That is a negative result about the
  repair, and the report names the stage.
- **A win that `accept.py` refuses.** An independent re-measurement on a clean
  worktree with its own bindings that comes back `rejected` or `no-control`
  means the search is producing plausible-but-wrong candidates — a real result
  about the gate ladder, reported as such, not as a failed run.
- **The cross-check firing.** If `control.crosscheck` disagrees with
  `reproduce.sh`'s published row, no result of the run can be trusted until a
  person says whether the toolchain moved or the design changed. That is a
  stop, not a datum.
- **A `tamper` verdict** on a run that should have been clean is, in practice,
  another agent editing a checkout mid-measurement — suspect that before the
  candidate (`docs/source/extensions/chia.rst`, guard 4).

## What this run cannot show

n=1 per arm, as every CHIA run so far has been. **No rate of discovery is
demonstrated by it**, in either direction, and a win would be one win, not a
capability. Two workers with different angles are two samples of a search, not
a comparison of two methods.

## Secondary 1: **one win, and it is the rediscovery this page predicted**

`accept.py`, on a clean `git worktree` with its own `mlir/` build, against a
control it measured itself in the same run before the diff existed:

```
claim  win
cosim    175 / 265 / 386 / 435 / 627
control  175 / 265 / 421 / 482 / 674   (measured in this run, vouched, pristine)
delta      0 /   0 /  -35 /  -47 /  -47   total -129
bench_isa ALL EXACT   stress 492/492   param OK at MAXDIM 8, 12 and T=8/MAXDIM=32
five cosim testbenches bit-exact; TPU_TB=stress 0 mismatches over 6 calls a shape
estimated clock 2.431 ns (target 3.33)   spec policy clean
cross-check: agrees exactly with reproduce.sh's published row
```

The diff is 22 lines across two files:

* `microarch_isa.py` — `_WIDEN = TpuParams.widest_burst(T, MAXDIM)`, deleting
  the `TPU_DMA_WIDEN` gate, so the widened operand burst is **on by default**.
* `ip/tinytpu.py` — the `ac2sp` channel (accumulator to `dma_st`) deepened from
  `QD` to `32`.

**This page predicted the first half by name before the run.** `TPU_DMA_WIDEN`
was already in the tree and off by default; the agent could not switch it on
through the environment, because every `TPU_*` variable is scrubbed, so it
changed the default. That is a **rediscovery of a lever already in the tree**,
and recording the prediction beforehand is what makes saying so a check rather
than an argument. The second half, the channel depth, was not predicted.

## Secondary 2: **the workers edited units, not the instantiation**

Across all six candidates the files touched were
`ip/units/dma_load.py`, `ip/tinytpu.py`, `ip/units/sequencer.py`,
`ip/assembler.py` and `microarch_isa.py` (the last only in the winner, for one
line of parameter default). **Nothing edited the old two-file surface alone**,
and four of the six candidates could not have been expressed at all under the
`EDITABLE` set the harness had before this repair. The decomposition is what
gave the loop its reach back, and this is the evidence for it: behaviour, not
a file listing.

## What went against the prediction

I predicted "0 or 1 accepted wins, `not-better` the most likely per-candidate
verdict". That is what happened -- 1 win, five `not-better` -- so the
prediction held, but it held for a softer reason than I expected. I expected
the headroom to be spent. It was not: **-129 cycles over five shapes** is a
7.0% reduction at 16x16x16 and 9.8% at 16x16x8, from two one-line changes.

## Two findings the run produced that this page did not ask for

**A recorded negative was rediscovered from three lines away.** `front-end`'s
iteration 1 merged `dma_ld`'s two operand-burst loops into one bounded by
`max(a_rows, b_rows)`. `ip/units/dma_load.py:45` -- in the file the agent was
editing, three lines above the loop it rewrote -- says that change "was
measured to move nothing", and names the reason (the bursts are already hidden
behind the sequencer's prefetch). It scored 175 / 674: unchanged, exactly as
the note said. The information was in-band, adjacent and specific, so this is
not an artefact of anything withheld. A hypothesis worth a designed test, not a
result at n=1: a unit-scoped edit is badly placed to weigh a whole-pipeline
fact, so the decomposition that restored the loop's reach may also have made
locally-plausible global nulls easier to propose.

**The billing instrument failed live, across the whole run.** Every one of the
four large iteration calls ran the full 2400 s CHIA timeout and returned no
`usage` at all. On the `usage` field this run reads **$0.00**; on opencode's
database it reads **$20.72**. The known form of this defect was a single call
billed $4.33 and reported as $0.00; this is the same defect at run scale, and
it is why every cap here reads the database. `spend.json` in the run directory
has the per-session figures.

## What this run does not show

n=1 per arm, as every CHIA run so far. No rate of discovery, in either
direction. And one qualification that arrived from another track while this run
was in flight, recorded here rather than left to be discovered later: the
objective this run optimises -- summed cosim cycles at 4x4x4 and 16x16x16 --
is now known to be **partial**. The burst widening is worth **zero** cycles on
the model suite at the scored configuration while being worth real cycles on
these GEMM shapes, and worth -287 / -583 at `MAXDIM=64`; at `MAXDIM=16` a DRAM
row is four packed words rather than sixteen and the prologue hides the burst
for the models. So a **null** against this objective is weaker evidence of "no
headroom" than it looks, and a **win** against it is a win on GEMM shapes at one
configuration, not a win on the workloads. The pre-registration is left as
written; this paragraph is the deviation, in the results section where it can
be checked.

## Attribution of the win, measured afterwards ($0)

The win is two changes, so which one does the work is answerable without
spending anything: re-run `accept.py` on the burst-widening half alone, reusing
the control the first acceptance measured (`accept-burst-only/`).

| | 4x4x4 | 8x8x8 | 12x12x12 | 16x16x8 | 16x16x16 | total |
| --- | --- | --- | --- | --- | --- | --- |
| control | 175 | 265 | 421 | 482 | 674 | — |
| both changes | 175 | 265 | 386 | 435 | 627 | **-129** |
| burst widening alone | 175 | 265 | 386 | 435 | 627 | **-129** |

**Identical, shape for shape.** The `ac2sp` channel deepening from `QD` to 32
is worth **exactly zero cycles** over the five shapes, and the entire win is the
half this page predicted by name before the run.

This agrees, from an independent measurement and a different harness, with what
the objective work on another track found: `channel_depth` sums to zero over
the five published shapes. That track also found what the depth change *does*
buy -- three legal programs going from hanging to bit-exact -- and that **no
term in either objective scores it**. So the agent proposed a change that the
objective cannot see the value of, kept it because the objective did not
penalise it either, and it rode along inside an accepted win. That is worth
saying plainly: **this objective would have accepted the depth change for no
reason, and would equally have discarded it for no reason.** Neither is a
judgement about the change.

Both halves also passed every gate on their own: `bench_isa` ALL EXACT,
`param_check` exact at all three configurations, the `TPU_TB=stress` RTL
testbench clean, 2.431 ns.
