How the unit was expressed
--------------------------

* ``native`` (``cosim_native.py``) is ``out[k] = a[k] + b[k]`` on
  ``bf16[N]``, the same kernel shape as Kai's
  ``tests/rtl/test_ports.py::test_narrow_floats_cross_the_host_boundary``.
  RTLGen has bf16 (``allo.lang.bf16``). Its float operators are the archetypes
  in ``allo/backend/rtl/devices/ip.py`` (``bfadd``/``bfsub``/``bfmul``,
  ``bf2f``, plus f16/f32/f64). They bind only to Vivado ``floating_point``
  cores (``devices/vivado.py``): bf16 is spelled ``Custom`` with an 8-bit
  exponent and an 8-bit fraction. None of them has an RTL body.
* ``bits`` (``bits_kernel.py``) mirrors the ``.sv`` statement by statement on
  ``i32`` locals with ``u16[N]`` ports: the align shift capped at 10, the
  add/sub of 17-bit significands carrying 9 extra low bits, a sticky right
  shift on carry, a normalize capped by the exponent, RNE on guard, round
  and sticky, and specials first. The one structural change is the leading-
  zero count. The ``.sv`` uses a ``for`` loop with a ``found`` flag; here it is
  a 5-step priority search. The loop form is probed separately as F4.
  ``bits_scalar_kernel.py`` is the same body with ``(u16, u16) -> u16``
  scalar ports.

Neither variant stopped with an error. Both produce SystemVerilog headed
``// Generated by CIRCT af5369d``, with ``clk``/``rst``/``start``/``done``
control and arrays as external memory ports (``A_rd0_addr``/``A_rd0_data``,
``C_wr0_*``).

Findings
--------

**F1 (native): semantic mismatch.** RTLGen's ``bf16 +`` is IEEE, and nothing
in the frontend can state the unit's own NaN and zero rules.
The 1,941 mismatches break down as follows:

* 1,940 have a NaN on both sides. RTLGen keeps the operand's sign and payload
  and quiets it, while MiniTPU always gives ``+0x7FC0``. For example,
  ``0x0000 + 0x7F81`` gives ``0x7FC1`` against ``0x7FC0``, and
  ``0x0000 + 0xFFFF`` gives ``0xFFFF`` against ``0x7FC0``.
* 1 is ``0x0000 + 0x8000``: RTLGen gives ``+0`` (IEEE), MiniTPU gives ``-0``.

RTLGen also differs from the IEEE reference ``ref.ieee_bf16_add`` on 1,855
vectors, all of them NaN payloads: IEEE-RNE through ``f32_to_bf16_rne`` gives
a canonical quiet NaN with its sign. These are the same two non-IEEE rules as
the Allo-simulator ``native`` cell. Here the NaN rule is a third one: payload
propagation. The source is the cosim model ``allo_st_bf16`` in
``sim/ip_models.py``, which writes ``(u >> 16) | 0x40`` for a NaN.

**F2 (native): missing abstraction.** No synthesizable adder exists, so
``native`` checks a C model rather than RTL. The emitted module instantiates
``add_bf16_bf16_bf16_l4 u0 (.a, .b, .clk, .ce, .y)`` and contains no
definition for it. Linting it alone fails:

.. code-block:: text

   %Error-MODMISSING: native.sv:41:3: Cannot find file containing module: 'add_bf16_bf16_bf16_l4'

In ``.cosim()`` that module is a DPI-C behavioural model
(``sim/ip_models.py``: the bf16 operands are loaded as ``float``, added in
``float``, and stored back with RNE). The 249,995 matches therefore show that
the C model agrees with MiniTPU, not any hardware. The real core is a Xilinx
``floating_point`` IP. Its documentation (PG060) says it flushes subnormals
to zero, and 2,334 of the 251,936 vectors have a subnormal input or result.
That claim comes from PG060 and was not measured here: there is no Vivado run
on this path. Supplying the unit's own RTL for the operator is not possible
either:

.. code-block:: text

   allo/lang/ip.py:140  def add_rtl_model(self, *arg, **kwargs):
                            raise NotImplementedError("add_rtl_model is not implemented yet")

The only user hook is ``add_c_model``, which changes cosim only. All devices
are FPGA devices, so there is no ASIC operator row for a bf16 add. For the
open ASIC flow of D-1, the ``native`` path gives no RTL at all, and ``bits``
is the only route.

**F3 (bits): missing abstraction.** No kernel can be zero-latency or
combinational. Every kernel gets ``clk, rst, start, done``. The scalar-port
``bits`` kernel takes 6 cycles at 300 MHz (467 FF) and 1 cycle at 50 MHz or
below (17 FF, fmax 72 MHz); 0 is never reached (``probe_freq.py``,
``probe_scalar_cosim.py``). The MiniTPU unit is a bare ``always_comb`` module
with latency 0, so an RTLGen version can stand in for it only behind a
registered handshake. A port-compatible drop-in needs a hand wrapper, which
is a workaround if it is ever used. Function is unaffected, because 20 of 20
scalar cosims matched at both clocks.

**F4 (bits): semantic mismatch.** A ``for`` loop means space in SV and time
in RTLGen. Written the way the ``.sv`` writes it (``bitsloop_kernel.py``:
``for j in range(17)`` with a ``found`` flag), the leading-zero loop is not
unrolled. The pipelined outer loop then falls apart, and the only signal is a
warning:

.. code-block:: text

   WARN: [PREP] Conditional left as an opaque scheduling unit because 'affine.for' cannot be predicated; the enclosing loop cannot pipeline across it (at 'er' bitsloop_kernel.py:61:12)
   WARN: [PREP] Conditional left as an opaque scheduling unit because 'scf.if' cannot be predicated; ... (x8, every if/elif of the result chain)
   INFO: [SCHED] Detected imperfect nest, decomposing into sub-regions scheduled in program order.

The result is still correct (64/64), but it takes 2,163 cycles for 64
elements, with the ``k`` region at II=48 (about 34 cycles per element against
1). One directive, ``s.unroll("j")``, restores II=1 (73 cycles for 64, 3,472
LUT; ``probe_loop_unroll.py``). Inside ``always_comb`` the ``.sv`` loop is a
priority encoder. In RTLGen it is a sequential loop unless it is unrolled,
and RTLGen does not unroll a constant 17-trip loop inside a pipelined body by
default. This is the same mechanism (an opaque nested op poisons
if-conversion) that the exploration record measured as per-instruction
fill/drain.

**F5 (bits): missing abstraction, QoR only.** Intermediate widths are not
narrowed from value ranges. The exponent, the shift and the leading-zero
temporaries stay 32 bits wide in the emitted SV (37 lines declaring ``[31:0]``
in the scalar module). The critical path is ``addi``, ``select``, ``minsi`` and
``shli`` at 32 bits (3.309 ns, slack 0.024 ns at 300 MHz). Declaring the
same locals as a 26-bit ``APInt`` instead of ``i32`` (``bits26_kernel.py``)
cuts the estimate from 2,175 to 1,794 LUT and from 655 to 579 FF, and still
matches. ``narrow-demanded-bits`` does not get there by itself.

Frontend notes (no finding class)
---------------------------------

* A ternary whose branches are both constants is rejected even when it is the
  right-hand side of an annotated assignment:

  .. code-block:: text

     bits_kernel.py:23:19: error: Cannot deduce the type of a ternary whose branches are both compile-time constants, as the bit-width would have to be guessed. Annotate one branch with its intended type (e.g. `cast(<value>, int32)`) or assign through a typed variable.
     23 |         ha: i32 = 65536 if ea != 0 else 0

  ``ha: i32 = ...`` is itself an annotation, but it does not count. ``i32(65536)``
  is rejected with "only allo kernel functions, operations, and consteval
  functions can be called", and ``cast`` is
  ``allo.operators.arith.cast``, not ``allo.lang``. A typed local constant
  (``H16: i32 = 65536``) works.
* Kai's frontend rejects shadowing a parameter with an annotated local
  (``Variable 'x' is already defined in the current scope``), which is
  reasonable.

Not done
--------

* No Vivado or Yosys synthesis: all area and timing numbers are RTLGen's own
  QoR model on u55c. The CP-SAT scheduler was not used (default SDC).
* No ASIC ``Device`` was written, so F2's "no RTL for ``native``" stands.
* The Verilog of the 251,936-vector ``bits`` run was not driven through
  ``harness/rtl.py``. RTLGen's arrays-as-memory-ports interface needs a
  memory model, which RTLGen's cocotb cosim supplies. The comparison is
  against the MiniTPU RTL outputs from ``harness/rtl.py`` (``vs_minitpu.py``).
