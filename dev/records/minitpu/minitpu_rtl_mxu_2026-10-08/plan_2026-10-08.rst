1. Interface map: ``mxu.sv`` vs the Allo MXU's Catapult RTL
============================================================

**MiniTPU's side** (``src/core/mxu/mxu.sv:5-30``; instantiated once in
``vpu.sv:251`` at ``DIM = NUM_LANES`` behind ``mxu_serializer`` /
``mxu_deserializer``):

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - port
     - contract (Phase 0, ``u3_phase0_2026-10-04.rst``)
   * - ``clk_i``, ``rst_ni``
     - one clock, async active-low reset
   * - ``input_push_i``, ``input_kind_i`` (RHS/LHS), ``input_data_i[DIM][16]``
     - pushed **blindly** by ``mxu_stream_engine`` (``mxu_input_push_o = busy_o``, no stall path); ``mxu_matrix_ctrl.sv:93`` only *asserts* ``!(push && !ready)``
   * - ``input_ready_o``
     - the input FIFO's not-full; 1 in every reachable state (the FIFO drains every cycle)
   * - ``input_accept_o``
     - ``push(t-1)``; the stream engine asserts ``!commit_q || accept`` the cycle after a load's last row
   * - ``weight_commit_i``
     - pulse with the last RHS row accepted; bank toggle
   * - ``output_pop_i``, ``output_valid_o``, ``output_data_o[SUB][DIM][16]``
     - the pop engine **waits**: ``beat_fires = popping_q && output_valid_i`` (``mxu_pop_engine.sv:35``), pops one group and writes the VREG in that cycle; a pop while not valid is ignored by the MXU
   * - timing the sequencer books (``docs/isa_latency.json`` ``matrix``)
     - ``result_latency.vmatpush`` 85 = 4 rows + (2 + DIM (PE+1)) - 1; ``issue_interval.vmatpop`` 1; ``weight_switch.span`` 75; ``resources.mxu_output_fifo.depth`` 64; ``rtl_params.WB_W_MPOP_{FIRST,LAST}`` 3/3; the bundle delay field is **7 bits** (``DELAY_W``, max 127 cycles per bundle)

**Allo's side.** The M1 ``lockstep`` composite (``examples/minitpu/units/mxu_unit.py``:
``mxu_front`` -> ``pe_unit`` D x D over depth-2 Streams -> ``mxu_back``) is a
*trace* form: every port is an array indexed by the token ``t`` (the token is
``mxu.sv``'s cycle), and the kernels run ``for t in range(N)`` then stop. Through
the SystemC emitter + Catapult (track C, ``u3c_build.py``) the region top is
an ``SC_MODULE`` with: ``clk``, ``rst`` (async, active **low**:
``async_reset_signal_is(rst, false)``), ``done``, and one Connections port per
region argument in argument order -- ``In`` for the inputs (``rst``, ``push``,
``kind``, ``data``, ``cmt``, ``pop``), ``Out`` for the outputs (``rdy``,
``acc``, ``vld``, ``odata``), each ``<v>_dat/_vld/_rdy`` in the RTL
(``ccs_conn_in/out_wait``). Two things stand between that and ``mxu.sv``'s
port list:

* **C1 (track C): a lane array is not a port.** As landed, ``input_data_i`` is
  ``UInt(16)[N * D]`` and ``output_data_o`` ``UInt(16)[N * D * SUB]``: read D
  (written D SUB) words per iteration, so the emitter makes them **RAM pins**
  (``_radr/_re/_q``), one word per cycle, and ``mxu_front`` cannot be II = 1
  (74 cyc/row at DIM 4, push->valid 1,631 cycles). The form used here,
  ``forms/mxu_wide.py``, packs them into ``UInt(16 D)[N]`` and ``UInt(16 D
  SUB)[N]`` (sublane ``s`` of lane ``c`` at bits ``16 (s D + c)``, the RTL's
  own packing): then **every** region port is a Connections stream. The
  back's lane rings (``mem: UInt(64)[D * ENTRIES]``) are a ``ccs_ram_sync_1R1W``
  unless partitioned (``--partition mxu_back_w_0:mem``, the ``vpu_regfile``
  precedent) -- without it ``mxu_back`` "could not schedule even with
  unlimited resources" at II = 1 (SCHD-30, the first run here).
* **Token time vs cycle time.** The core consumes one token per port per
  iteration; the token index is the cycle *of the model*. In the RTL a token
  travels front -> grid -> back through Connections FIFOs, so the output
  tokens lag the input tokens by the grid's pipeline depth. ``mxu_allo.sv``
  (generated by ``scripts/gen_mxu_allo.py`` from ``kernel.cpp``, so the port
  numbering follows the build) is the adapter:

  - module name ``mxu``, ``mxu.sv``'s parameter and port list unchanged (so
    every MiniTPU tb and ``vpu.sv`` instantiate it as is); elaboration
    ``$error`` if ``DIM``/``NUM_SUBLANES``/``OUTPUT_FIFO_DEPTH`` differ from
    what the core was built at (an Allo core is one geometry);
  - one wrapper FIFO per In port, pushed every clock (``rst_ni``,
    ``input_push_i``, ``kind == RHS``, the packed data, ``weight_commit_i``,
    ``output_pop_i``), drained by the core's ``_rdy``: a core stall delays
    tokens instead of losing them, and a FIFO that fills is a flagged
    **lockstep violation** (throughput below one token per cycle), never hidden;
  - every Out port always ready; ``input_ready_o`` / ``input_accept_o`` /
    ``output_valid_o`` / ``output_data_o`` are the latest ``rdy`` / ``acc`` /
    ``vld`` / ``odata`` tokens, registered;
  - the **pop mask**: a pop MiniTPU issues at cycle ``c`` is token ``c``; its
    effect is in ``vld`` token ``c + 1``, which arrives ``lag`` cycles later,
    and until then the shown head is stale. ``output_valid_o = vld_q &&
    (vld_tokens_received > last_pop_token)``, so the pop engine never pops a
    stale head and never writes a stale VREG. This is what turns the lag into
    ``issue_interval.vmatpop``;
  - reset: ``rst_ni`` drives the core's ``rst`` and the ``rst`` token (D-14's
    control clear in ``mxu_unit``); ``input_kind_i`` is the enum, mapped to one
    bit;
  - probes (not contract ports): ``lag_o`` = input tokens - ``vld`` tokens,
    ``acc_lag_o`` = input tokens - ``acc`` tokens, ``lockstep_violation_o``.

  Clock enable: none on either side (E03's ``en_i`` is not at ``b3ba0a4d``).

2. Which MiniTPU testbenches can judge a slower MXU
===================================================

* ``tb/tb_mxu_single_port.sv``: ``DIM = 2`` hard-coded, imports only
  ``vpu_pkg``, and **waits** (``wait (output_valid)``) -- latency-agnostic.
  It runs unchanged against any MXU with ``mxu.sv``'s ports. It checks one
  identity tile at the ``mxu`` boundary and one pop: the acceptance check
  for the wrapper, not for the ISA timing.
* ``tb/tb_matrix_command_ii.sv``, ``tb_matrix_weight_pipelining.sv``,
  ``tb_matrix_weight_banks.sv``, ``tb_matrix_full_vreg.sv``: vpu-level
  (``vpu dut (.*)``, the real sequencer side), DIM = ``NUM_LANES`` = 16. The
  numbers come from ``tb/isa_latency_pkg.sv`` (``DOC_VMATPUSH_RESULT_LATENCY``,
  ``DOC_MATRIX_WEIGHT_SWITCH_SPAN``, ``DOC_VMATPOP_ISSUE_INTERVAL``, ...),
  **generated** by ``tools/gen_isa_doc.py --write`` from
  ``docs/isa_latency.json`` -- not hard-coded in the tb, but ``command_ii``
  *measures* each and fails unless it equals the package, and ``weight_
  pipelining`` schedules commands from them. So they run against a slower
  MXU exactly when the package is regenerated from the version's numbers:
  a ``versions``-aware ``gen_isa_doc.py`` (their master, not ``b3ba0a4d``)
  resolving ``versions.list.allo-mxu`` -- the seam's intended use -- and
  the RTL constants ``tb_isa_conformance`` compares (``WB_W_MPOP_*``,
  ``MXU_OUTPUT_FIFO_DEPTH``, ``MXU_WEIGHT_BANKS``) must be the same in
  ``vpu_pkg``/``sequencer_pkg`` (``WB_W_MPOP_LAST`` is derived from
  ``MXU_POP_BEATS``, unchanged here).
* The sequencer itself has no latency constant for the MXU
  (``sequencer_pkg.sv:32`` only sizes the 7-bit delay field "so one field
  covers the 85-cycle result latency"); ``asm.py`` schedules by
  ``_M_RESULT_LATENCY = 85`` (``board_package/asm.py:830``, generated from
  the JSON) and inserts filler delay bundles when a gap exceeds 127. A
  result latency above 127 therefore costs bundles, not correctness.

4. The timing answer, and the three options
===========================================

The Allo MXU is a cycle model in **token time**; in the RTL tree the token
lag against MiniTPU's clock is what MiniTPU's sequencer would see as extra
result latency, and it is only a number if the core sustains one token per
cycle. Two facts decide the options:

1. **The rate is the link depth against the geometry, not the kernels.**
   With every kernel at II 1 (every manifest), depth-2 Connections links
   between PEs whose two inputs arrive from different pipeline depths
   sustain 2/3 token per cycle at DIM 2 and 0.4 at DIM 4; depth 4 sustains
   1 at DIM 2 and 0.6 at DIM 4. The needed depth grows with the arrival
   skew (up to DIM - 1 tokens at DIM 16), so it is a per-geometry
   composition parameter and a D-20 legality, not a unit property.
   ``pe_channels``'s "2" is right on the untimed simulator and wrong on
   timed RTL. The next probe is DIM 4 at depth 8 and 16 (17 min per build);
   a lag that does not settle at depth ~DIM says the grid needs the
   Wire-locked form (option a) rather than deeper FIFOs.
2. **At one token per cycle the lag is a constant** (8 at DIM 2), so option
   (b) is exactly the seam's case: ``result_latency.vmatpush`` = MiniTPU's
   + lag + 1, ``issue_interval.vmatpop`` = lag + 1 (the wrapper's pop mask,
   without which the pop engine writes a stale head), ``acc`` lag 1 (so the
   stream engine's commit/accept assertion holds since 1 < DIM).

* **(a) cycle-locked grid (A2, Wire links, H8)** -- the lag goes to ~2 by
  construction (front and back I/O only). Needs ``Wire[T, comb]`` links on
  the grid (D-13; emitter path run on single kernels only), a ``pe_unit``
  whose outputs are edge-written registers (the cycle-equal ``bits`` PE is
  that), one SystemC module for the D x D grid. ~1 day for the form; the
  build time at DIM 16 (hours per attempt) is the real cost. Payoff: a
  version that differs from ``v1-course`` by a constant 1-2 cycles.
* **(b) declared version** -- works now at DIM 2 (depth 4). What the full
  version needs: the DIM-16 build (overnight), the span measured at the
  ``mxu`` boundary, the delta written by ``gen_isa_delta.py`` at DIM 16 and
  landed through ``minitpu-comp``'s ``versions`` PR, ``asm.py`` scheduling
  from it (the 7-bit delay field only costs filler bundles above 127), and
  the ``tb_matrix_*`` tbs regenerated from the version (section 2).
* **(c) which tbs count** -- ``tb_mxu_single_port`` (as is) is the wrapper's
  acceptance; ``tb_matrix_command_ii`` + ``tb_matrix_weight_pipelining`` at
  the version's numbers are the ISA-timing oracle; ``tb_matrix_full_vreg``
  / ``weight_banks`` the data oracle at vpu level; the board gate is the
  MiniTPU owner's.

5. What the full integration needs
==================================

1. ``Channel.depth`` per grid link chosen per geometry and checked (a
   legality: the rate at one token per cycle, measured by the wrapper's
   lag counters on a long idle run) -- the only Allo-side change the probe
   asks for, and it is a composition parameter, not core code.
2. The DIM-16 ``mxu_wide`` build through Catapult (overnight; or D-7's
   answer, DIM 2/4 instances as the oracle shape and the DIM-16 build as
   the once-per-version evidence), with the front's arrays partitioned
   (``skd`` is 976 x 16 at DIM 16) -- a declared register array
   (D-12's ``Memory(ports=)``) would say so in the source.
3. ``mxu_allo.sv`` as generated (``gen_mxu_allo.py``; the port numbering
   follows each build), in MiniTPU's compile list in place of ``mxu.sv``
   for the unit and vpu suites; the deserializer/serializer and ``vpu.sv``
   unchanged.
4. The ``versions.allo-mxu`` delta from the DIM-16 measurement
   (``gen_isa_delta.py``, plus the span), landed as the agreed PR to
   ``minitpu-comp`` (their ``versions`` branch), ``tb/isa_latency_pkg.sv``
   regenerated for it, ``tb_matrix_*`` run at those numbers, ``asm.py``
   scheduling a program at the version and the bundle-level tbs run on it.
5. The board gate (bitstream, host runs) stays with MiniTPU's owner.

6. Owner decisions
==================

1. **Cycle-locked (a) or declared (b)?** Provisional here: **(b) first,
   gated on the depth sweep at DIM 4** -- (b) works today at DIM 2 and is
   the seam's intended use; if no depth settles the lag at DIM 4, (a) is
   the only form with a number, at a day's form plus hours-scale builds.
2. **Which MiniTPU tbs are the oracle for the Allo MXU?** Provisional:
   ``tb_mxu_single_port`` (unchanged) for the wrapper; ``tb_matrix_command_ii``
   and ``tb_matrix_weight_pipelining`` regenerated at the version for the
   timing; the board gate is MiniTPU's owner's.
3. **Link depth as a legality** (D-20): accept that a composition's channel
   depth is per geometry and checked by a rate measurement, or require the
   Wire-locked grid so that no depth exists to choose.
4. **DIM 16 overnight build**: schedule it (and at which link depth: 4, or
   DIM) before writing any DIM-16 number anywhere.
