Method (U3 track D's, reused). The Phase 0 oracles are dumped once from the
Allo env (``dump_oracles.py``: exactly ``check.py``'s joined trace per unit,
the RTL's response from ``harness/rtl.py`` and the defined-slot mask; RTL ==
reference on every defined slot asserted at dump time; counts equal the
matrix's: ``dma_addr_gen`` 200,700 vectors, ``seq_decoder`` 25,458,
``agu_resolve`` 38,432, ``vpu_adapter`` 24,866, ``scalar_agu:lat2`` 201,065
defined slots on 40,214 cycles, ``dma_desc_adapter`` 180,495 on 20,056). The
tools then run in their own environments and compare with ``verdict``, the
``check.py`` defined-slot rule. A stateless unit runs in chunks of ``N`` rows
(one cosim per chunk); a stateful one (``scalar_agu``, ``dma_desc_adapter``)
runs as **one** kernel call over the whole trace, one iteration per cycle,
``pre`` outputs first and then the edge (the trace convention), so its match
is **per cycle**.

Forms. Every unit is first run **as written** -- track A's / C's Allo body
with only the type names respelled for the tool (``UInt(46)`` ->
``apint(46, signed=False)`` in RTLGen; AMC's frontend takes ``UInt(k)``), and
the C1 functions kept as **called functions** (``*_call`` / ``written``) --
and then in the form the tool needs: the function body **inlined** into the
row loop (generated text, as U3's tree), lane-array ports **split** into 1-D
ports where a lane array cost II, and for AMC U1's workarounds (A2 single bits
as ``x[k:k+1]``, A4 inlining, A8 slice stores as shift-and-or, A5 two-operand
booleans) plus U3's register discipline (A-D3) for state. Every form is in
the scripts below; nothing was hand-edited after generation.

1. Verdicts (per unit, per tool)
================================

**match** = every defined slot of the Phase 0 oracle equal on the whole
trace/stimulus (no prefix anywhere below unless named). Cycles are the
tool's cosim count for a chunk of ``N`` rows: both tools wrap a function in
a ``start``/``done`` kernel over array ports (U1 F3/P1), so the
latency the tool adds is the count minus ``N`` (``N + k``) at II=1. Area:
RTLGen's QoR model on ``u55c`` at 300 MHz; AMC: Vivado OOC at 3.333 ns
(section 7). Not like for like.

2. The D-12 memories through AMC
================================

AMC's memory lowering was driven two ways: (a) **its own memory
declaration** -- an ``amc.memory`` whose ports are the D-12 ``Port``\ s
spelled as AMC port types (``amc/mem/*.mlir``; ``amctool --memory-only
--emit-verilog``), which is the place AMC can be *told* a port; and (b)
**its frontend**, a trace kernel that owns the memory as a local array, one
host write and one read per iteration (``mem_frontend_amc.py``), where
AMC's allocation *infers* the ports. The emitted SV of (a) was then held to
the D-12 declarations in Verilator (``amc/mem/tb_mem.sv``, 10/10 checks,
``logs/amc_mem_tb.log``).

.. list-table::
   :header-rows: 1
   :widths: 18 26 56

   * - memory (D-12 declaration)
     - AMC spelling
     - result
   * - fetch ``f1_d12`` IRAM: ``UInt(128)`` x 4,096,
       ``Port("host", "w", visible=1)``, ``Port("fetch", "r", latency=1)``,
       ``collision="refuse"``, ``reset=False``
     - ``static w(1)`` + ``static r(1)`` on ``!amc.ram<4096xi128>``
     - **accepted, lowers to the declaration.** ``reg [127:0]
       mem0[0:4095]`` with an empty reset branch (unreset storage, as D-14
       asks), a write at the edge, a registered read (``rd_hold_s0``) that
       **holds** while ``rd_en`` is low. Verilator: data one edge after the
       address; a write visible the next cycle; a read of the row being
       written returns the **old** word (D-12 says "refuse" -- the
       composition promises it never happens; AMC has no collision
       attribute and builds "old", d12_memory_ports' prediction). Through
       the frontend (b): ports inferred as ``dyn w(1)``, ``dyn r(1)``,
       ``dyn w(1)`` (the zero-initialising loop is a third port; an
       unannotated local ``m: UInt(128)[4096]`` has no init loop), match
       unscheduled; pipelined prints ``problem is infeasible`` and still
       matches
   * - ``loop_ctrl`` ``l1_d12`` loop buffer: ``UInt(128)`` x 24,
       ``Port("cap", "w", visible=1)``, ``Port("replay", "r", latency=0)``,
       ``collision="refuse"``, ``reset=False``
     - ``static w(1)`` + ``static r(0)``
     - **accepted, lowers to the declaration**: ``assign p1_rd_data =
       mem0[p1_addr]`` (asynchronous, ``done = rd_en`` combinationally),
       unreset. Verilator: combinational read, an address change seen
       without an edge, a write visible the next cycle, same-cycle read of
       the row being written = old. 24 rows on a 5-bit address: rows 24..31
       are not checked (an out-of-range read returns whatever the array
       model gives). Through the frontend (b): the read becomes ``dyn r(1)``
       -- **the frontend cannot ask for a latency-0 port** (it has no port
       API; d12_memory_ports' gap) -- unscheduled match; **pipelined prints
       ``problem is infeasible`` and returns a design that computes wrong
       read-back values** (the class of the AMC #126 comment, a failed
       schedule still returns a design)
   * - ``dma_vmem`` VMEM: ``UInt(1024)`` x 4,096, ``Port("c", "rw",
       latency=3, visible=1)``, ``Port("d", "rw", latency=2, visible=1)``,
       ``collision="obligation"``, ``reset=False`` (H11)
     - ``static rw(3, 1)`` + ``static rw(2, 1)``

       ``d`` 2 (latencies as declared); (ii) both ports ``rw(1, 1)`` with
       the extra stages outside the memory. In (ii) two writes to one row in
       one cycle leave **port 0's** word silently (fixed priority by
       statement order): D-12's ``collision="obligation"`` has no
       counterpart and no check (semantic mismatch, recorded, not judged)

**H11 answered for AMC:** the DMA port beside the compute port can be
*stated* in AMC's own IR (two ``static rw`` ports of different latencies on
one bank) but not *lowered* at fe60c121 (E-A3). Nothing in AMC refuses II=1
on a read-or-write port the way Catapult does (``asic_memories`` s.2.2); the
dual-ported ``seq.hlmem`` is a behavioural array, not a macro.

3. Hypotheses
=============

* **H1 (C1 functions match first time; RTLG/AMC refuse a ``comb`` port,
  take a registered one).** RTLGen: **yes** -- every C1 function
  (``addr``/``addr_gen``, ``resolve``, the seven ``decode_*``, ``adapt_v/x/m``
  and the gated deviation) matched at the first run in every form, inlined or
  called, with only the type names respelled; RTLGen's frontend takes
  Allo's bit-slice reads, slice stores and single-bit indexes as written.
  AMC: **no** as written (A2 refuses every slice-heavy body; A4 aborts on
  every called function); **yes** once inlined and rewritten with U1's
  workarounds -- plus one new one, typed constants for shifts past bit 31
  (E-F1, which is Allo's too). The second half of H1 does not arise: neither
  tool has a port-level choice between a combinational and a registered
  port. Both wrap the function in a ``start``/``done`` kernel over array
  ports, so the C1 function is "registered" by construction. The added
  latency is a kernel depth: RTLGen N+1..N+4 and AMC N+2..N+6 for the
  comb units at II=1, with nothing pinned (D-10).
* **H2 (opt; S1 at ``latency=S_LAT``).** RTLGen: S1 matches **per cycle**
  at ``S_LAT`` = 2 (the shipped ``lat2``) in three spellings once E-R1 is
  avoided. The pipe is data, so the tool's own pipelining only adds kernel
  depth (N+4 at II=1 for ``regs_split``), as U3's PE. As written, it is
  silently wrong (E-R1). AMC: **blocked** (E-A6). ``lat1``/``lat3`` were
  not run.
* **H9 (opt; D1 ``dma``).** **Not run** (time went to E-R1/E-A6 and the
  memories). ``dma_desc_adapter`` (A1, the DMA's front) was run instead and
  matches per cycle on both tools.
* **AMC on the D-12 memories** (the plan's last line): IRAM and the loop
  buffer lower **exactly** to their declarations when stated as
  ``amc.memory`` ports, latency 0 included; the frontend cannot state
  them; VMEM's two ports are refused by a lowering bug (E-A3).

4. Findings
===========

Classified per D-9. ``E-R`` RTLGen, ``E-A`` AMC, ``E-F`` Allo.

RTLGen
------

**E-R1 -- bug, silent miscompile (high).** Inside a nested ``@kernel``, a
narrow unsigned **parameter** compared with a literal whose top bit (at the
parameter's width) is set is never equal: ``def is4(op: u3) -> u32: ... if
op == 4`` is false for every ``op``, on RTLGen's own ``cpu`` target as well
as in the RTL (so the frontend lowers it, not the backend). The same compare
on a local (``op: u3 = x`` inside the callee), at top level, or against 3
is right (``rtlgen/repro_param_cmp.py``, ``logs/rtlgen_repro_param_cmp.log``).
Presumably the literal is materialised at the parameter's width as a
*signed* value (4 in 3 bits = -4) and compared with the zero-extended
parameter. In S1 it turns every ``SSHL`` into a write of 0: 48,693 wrong
defined slots, no warning. Passing ``op`` as ``u32`` and narrowing inside
restores 201,065/201,065 (``written_e1``).

**E-R2 -- missing abstraction / QoR (U3 D3 again).** Every lane-array port
is a memory with two ports per cycle, so II = (accesses per iteration) / 2:
the decoder's and the adapter's 2-lane in/out ports give II=2, S1's
four-lane ``SREG`` output II=4, the descriptor adapter's ``IN[N, 6]`` /
``OUT[N, 9]`` (64-bit words, counted twice) II=9. The scheduler says so and
names the remedy ("Banking or replicating what this access reaches"); the
1-D-port spellings are II=1 everywhere. P-8's lane arrays are right for
Allo's backends and cost II here, as U3 recorded for the tree.

**E-R3 -- workaround (U3 D2 again): a called function is a sequenced
sub-region.** Every called C1 function decomposes the row loop ("Detected
imperfect nest, decomposing into sub-regions scheduled in program order"):
7 (addr), 9 (adapter), 13 (decoder), 15 (resolve) cycles per row, instead of
II=1 inlined. The values are right (no carried state). RTLGen has no
``inline`` directive (``Schedule`` has none; ``consteval`` is compile-time
only), so a library of C1 functions is reused at II=1 only by textual
inlining.

**E-R4 -- frontend notes (no class).** No ``u24`` alias in ``allo.lang``
(``apint(24, signed=False)``); host arrays at most 64 bits (lanes, as
Allo's); a ``u1`` used as a condition (``if agu_valid:``) is fine; S1's
``regs_split`` reaches only 249 MHz in RTLGen's model (the multiply, select
and add in one iteration, which is the RTL's own one-cycle path).

AMC
---

**E-A1 -- bug (loud).** A kernel named ``top`` builds on ``llvm`` and fails
on ``amc`` at FSM emission: ``error: redefinition of symbol named 'top'``
then ``RuntimeError: FSM verilog emission failed``. Renamed, it builds
(``amc/repro_top_name.py``). U1's R4 met the same message on a textual
hand-off and read it as a duplicate wrapper; it is the name.

**E-A2 -- bug (minor).** ``amctool --memory-only --emit-verilog`` prints the
SystemVerilog and then exits 4 with ``error: unknown operation
(SharedEmitterState::gatherFiles)`` on the ``amc.memory`` op left in the
module (every memory in ``logs/amc_mem_lowering.log``). The emitted SV is
complete; a script that trusts the exit code calls it a failure.

**E-A3 -- bug (blocks VMEM, H11).** A ``static rw(R, W)`` port with ``R !=
W`` is legal at the type level (``test/errors/dyn-rw-latency.mlir``: "Static
`rw` with split latencies is allowed") but cannot be lowered:
``AmcToHW.cpp`` ``unpackPortType`` folds the port to ``max(R, W)`` and
``lowerCreatePort`` passes that number to ``seq::WritePortOp``
(``AmcToHW.cpp:359``); ``LowerSeqHLMem`` refuses a write latency != 1 with
a ``notifyMatchFailure`` that surfaces only as ``failed to legalize
operation 'seq.hlmem'``. (For ``R < W`` the read would also be delayed to
``W``.) Minimal repro: ``amc/mem/repro_rw_split_latency.mlir`` (one
``rw(2, 1)`` port, 64 x i32).

**E-A4 -- note (E-F1 in AMC's lineage).** An untyped literal is ``int32`` in
AMC's frontend too: ``x | (1 << 35)`` on a ``UInt(64)`` leaves bit 35 clear.
It made the first hand-written decoder 11,953/25,458 on ``llvm``; typed
constants fixed it.

**E-A5 -- bug (testbench, minor).** AMC's Verilator testbench declares
each argument memory by the DUT's address width; a 2-D argument
``uint32[38432, 8]`` gets a 29-bit address and ``reg [31:0]
mem0[0:536870911]``, which Verilator refuses (``Width of bit range is huge;
vector of over 1 billion bits``). 1-D arguments of 40,214 rows build. The
workaround is chunks of 4,096 rows for a stateless unit; a stateful one
with 2-D arguments (S1's ``KA``/``IV``) would need 1-D lane ports.

**E-A6 -- bug, crash (blocks S1).** S1 in the A-D3 register discipline
(``llvm``: match 201,065/201,065) aborts the ``amc`` build on both schedules:
``error: 'loopschedule.await' op operation destroyed but still has uses`` /
``LLVM ERROR: operation destroyed but still has uses``; pipelined it first
prints ``problem is infeasible``. Greedy line deletion (``amc/ddmin.py``)
reduces the 175-line kernel to 55 (``amc/repro_sagu_await.py``): fifteen
1-element-array registers read at the top of the iteration, four stores
to a 2-D output, and a 2-deep pipe's five copies ``p1_x = p0_x`` under
``if live == 1``, each written back at the bottom. No single construct
alone triggers it. ``repro_cond_copy.py``: the copies under ``if`` alone build
and are right. **A-D2 is reachable at depth 2**: the *unconditional*
2-deep shift with the output read *before* the shift (S1's ``pre`` order)
aborts in ``LoopSchedule/Utils.cpp:442``. U3's repro reads after the shift
and needed depth 3.

**E-A7 -- instance of the filed #126 comment.** The loop buffer's frontend
kernel, pipelined: ``problem is infeasible``, then a design that simulates
and returns wrong read-back rows. No exception. Same class as #126's
A1 comment; one more repro (``mem_frontend_amc.py loopbuf amc pipeline``),
no new issue.

**Confirmed again (U1):** A2 (``Unsupported bit operation`` on
``seq_decoder``, ``vpu_adapter``, ``scalar_agu``, ``dma_desc_adapter`` as

Allo

**E-F1 -- bug, silent (Allo front end; repro
``tests/limits/new_wide_literal_shift.py``, REPRODUCES).** An untyped
literal is ``int32``, so ``y: UInt(64) = x | (1 << 35)`` leaves bit 35 clear
on ``customize(...).build("llvm")`` and on the dataflow simulator alike, with
no warning. It was found when the decoder was rewritten as shift-and-or for
AMC: ``1 << 56`` (``d.valid``) and every field above bit 31 vanished. No
landed U4 unit is affected: the Allo bodies use slice stores, not literal
shifts, and every Allo column matches. Workaround: a typed one
(``ONE: UInt(64) = 1``). Proposal: type a literal shift by its annotated
target, or refuse a shift amount >= the literal's width. Not added to
``limitations.rst`` here (docs are not this track's to edit); for the
integrator.

8. Provisional calls made (D-9)
===============================

* **P-E1.** The tools read frozen ``.npz`` oracles, not the harness (U3
  P-D1); the comparison is ``check.py``'s defined-slot rule.
* **P-E2.** A unit's verdict is taken on the form that the tool needs and
  that is still the same function: inlined bodies, split ports, and for AMC
  U1's rewrites and A-D3's register spelling. The as-written run is
  recorded beside it as the H1 evidence. No form changes a computed bit.
* **P-E3.** ``scalar_agu``'s RTLGen cell is the E-R1 **finding**, with the
  matches beside it: the as-written form is what a user would write, and it
  is silently wrong.
* **P-E4.** E-F1 is classed a **bug** (silent; the annotated target is
  64-bit), not a semantic choice. It is recorded as a ``tests/limits``
  repro, not as a limitations-register item: the docs belong to the
  integrator.
* **P-E5.** Only ``scalar_agu`` ``lat2`` was run; ``lat1``/``lat3`` were left
  out, since the pipe is data and ``S_LAT`` only changes the generated
  depth.
