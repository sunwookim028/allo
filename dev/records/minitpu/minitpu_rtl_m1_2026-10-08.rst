1. First test: a MemPort and stream ports on one IP
===================================================

M-R0 left this untested. ``mixed_probe.sv`` is one top with a 16-word
``MemPort`` (read, then write back ``+inc``) and two 32-bit ready/valid stream
``Port``\ s (command in, old value out), ``done`` after the last command; the
region has three kernels (``feed`` puts the program, ``core`` calls the IP
with the boundary array, ``sink`` drains the status stream)::

   MIXED trial 0: PASS st=[30, 50, 31, 0, 150, 35] ... mem[0,3,5,15]=[8, 67, 52, 166] want=[8, 67, 52, 166]
   MIXED trial 1: PASS ...  (a second call of the built module starts from reset: persistent=False)

**Verdict: works**, so the shim takes the RAM form (owner decision 2 of the
plan): the DDR image is Allo boundary memory served through ``MemPort``\ s,
and the command/status paths are streams on the same IP. ``ip.py``'s stream
wrapper already passes array arguments beside streams; nothing needed fixing.

2. The design
=============

The region (``minitpu_rtl.py``; ``architecture(ip)`` composes it,
``make_region(ip)`` is the same text as a plain ``@df.region``)::

   memories  P: int32[5152]          the program (gen_shim.CMD words)
             B0..B7: int32[2**20]    the 32 MiB DDR image, word-interleaved (bank k = bytes [4k,4k+4) of each 32 B DM word)
             W: int32[2]             drain window (first DM word, DM words)
             R: int32[262144]        the drain
             S: int32[16]            status words
   channels  cmd: Stream[int32, 4]   feed -> core
             st:  Stream[int32, 4]   core -> sink
   units     feed(P)                 for i < NCMD: cmd.put(P[i])
             core(B0..B7, W, R)      CORE(cmd, st, b0..b7)   -- the RTLModule call: one launch from reset
                                     then the drain copy B* -> R over W
             sink(S)                 for i < NSTAT: S[i] = st.get()

``compose.Architecture`` accepted it with the ``RTLModule`` object bound as
the parameter ``CORE`` (``calls=`` refuses it: not a function); its checks
(declaration == body, one writer/one reader per channel, memory binding) ran
and passed, and the 52 launches gave the same digests, cycles and status words
as the plain region (compared in full).

**The IP** (``make_ip``): ``RTLModule("minitpu_core_shim", core.f expanded +
shim, include_paths=[src/pkg], defines={"MINITPU_MXU_OUTPUT_FIFO_DEPTH": 64},
ports=[Port cmd (size=NCMD), Port st (out), MemPort m0..m7 (2**20 x int32_t)],
clock="clk", reset="rst_n" (active low), start=None, done="done",
persistent=False, verilator_args=["--build-jobs", "16"],
max_stall=20_000_000)``. ``validate_rtl`` (the ``--json-only`` port) passed;
the build gives no warnings; ``--lint-only -Wall`` reports only M-R0's
``SYNCASYNCNET`` on ``rst_n`` (the core's).

**The host program** is Allo arrays: ``program()`` writes
``IRAM n`` + the image's 4n little-endian words, the four ``kernel_arg_csr``
words exactly as ``tb_kernel_image`` computes them (``(ARG_BASE[a] +
offset) >> 5``, or ``+ARG_VALUEn`` as is), ``MAXCYC`` (the case's
``max_cycles``), ``START``, NOP padding and ``END`` last; ``ddr_image()`` lays
the kernel binary at ``MEM_BASE`` and window n at ``ARG_BASE[n]``, the
testbench's addresses, so every pointer and every 4 KiB burst split is the
testbench's. The digest is ``sha256`` of the first ``drain_bytes`` of the
drain window, as ``oracle.py`` takes it.

The shim's port map
-------------------

.. list-table::
   :header-rows: 1

   * - ``minitpu_core`` port (plan section 2)
     - Driven by / read into
   * - ``clk``, ``rst_n``
     - the shim's own pins = the transactor's clock and its 8-cycle reset per call
   * - ``start`` (pulse)
     - one cycle on the ``START`` command
   * - ``done`` (pulse)
     - latched; ends the run, then ``NSTAT`` status words go out on ``st``
   * - ``illegal_op_o``
     - sticky, status word 0 bit 3
   * - ``instr_write_en``, ``iram_addr[11:0]``, ``dma_iram_din[127:0]``
     - ``IRAM`` command: four ``cmd`` words per bundle, word 0 = bits [31:0];
       one registered write per bundle (the TB's ``iram_loader`` does the same
       from DDR; the shim skips the DDR round trip, which is outside
       ``perf_cnt_cycles``)
   * - ``program_id_csr[31:0]``, ``kernel_arg_csr[127:0]``
     - ``CSR k`` command + value word (k = 0..3 arg words, 4 program id; the
       TB never writes the program id, so it stays 0)
   * - ``dm_req_*`` / ``dm_rsp_*`` (256-bit credit pipe)
     - the eight ``MemPort`` banks, one DM word = one access per bank in one
       cycle; in order, one request in flight; out-of-window -> DECERR, no
       RAM access; partial ``wstrb`` counted (``MemPort`` has no byte enables)
   * - ``dma_err_o`` (+channel/cause/resp), ``dma_rsp_seen_o``,
       ``beat_count_o``, ``overlap_stat_o``, ``perf_cnt_cycles_o``,
       ``perf_cnt_instrs_o``, ``dma_channel_done_o``
     - status words 0-6
   * - (shim) run cycles, load/store words and requests, memory errors,
       partial-wstrb beats, bundles loaded, magic ``0x4D523101``
     - status words 7-15

Command words (``gen_shim.CMD``, opcode in [31:28]): ``NOP`` 0, ``IRAM`` 1
(``[27:16]`` first address, ``[15:0]`` n), ``CSR`` 2, ``START`` 3,
``MAXCYC`` 4, ``END`` F. ``launch_status`` (the AXI top's command-unit
register) does not exist at the core seam; its nearest equivalents are the
shim's memory-error and timeout flags, 0 on all 52.

4. The SFU tables: loaded, and proved loaded
============================================

The core ``$readmemh``\ s ``src/core/sfu/{gelu,exp}_bf16.mem`` by a
cwd-relative path (M-R0 section 2). The Verilated model runs inside the
Python process, so ``minitpu_rtl.run`` changes the process's working directory
to the MiniTPU export around the ``mod(...)`` call and restores it.
``run_kernel.py`` captures file descriptors 1 and 2 around each launch (the
model prints through C stdio, not Python) and counts ``$readmem`` lines; a
launch with any is never ``identical``. All 52 runs: **0** such lines.

Negative control (``--sfu-negative-control``: the same build, run from an
empty directory; ``negative_control.log``): every launch prints **128**
``%Warning: src/core/sfu/{gelu,exp}_bf16.mem:0: $readmem file not found``
(64 lanes x 2 tables) and runs on; ``gemm_varying_gelu`` drains ``80422bc3``
instead of ``d94353e8`` and ``softmax_8`` ``dfc81457`` instead of
``f2ed46f3``, while ``gemm_structured`` and ``layernorm_4`` (no GELU/exp) stay
identical. So the capture sees the warning when it happens, the tables matter
to the digest, and the 52 identical digests above ran with them loaded.

5. The cycle comparison
=======================

The table's ``cycles`` is the core's own ``perf_cnt_cycles_o`` (start to
``done``), the same counter ``tb_kernel_image`` reads (``dut.perf_cnt_cycles_w``);
the testbench's memory is ``axi4_mem_model`` at ``ROUND_TRIP_CYCLES=0`` (one
read burst at a time, data the cycle after the address) behind MiniTPU's
``uncore_io_tile``/``dm_axi_bridge`` (``OUTSTANDING=2``, landing FIFO depth 4,
AXI AR/R and AW/W/B hops). The shim's memory is none of that: the credit pipe
is answered directly from the RAM banks, one request in flight, a load's
first word one cycle after the request, a store's response one cycle after its
last beat.

Differences, -8,739 to +1,631 (42 launches fewer cycles, 10 more):

- **Fewer, by about one cycle per load request and two per store request on
  the critical path.** ``loop_begin_r.17``: 1 load + 4,369 single-word stores,
  -8,739 = -(1 + 2 x 4,369) exactly; ``head_scatter.0``: 16 + 16, -48 =
  -(16 + 2 x 16); the ``loop_begin_r`` set follows -(1 + 2 x stores) on all
  19. Where loads are prefetched behind compute (the GEMMs: 16 loads, -2) the
  saving shows only on the requests that are waited for. The testbench's
  extra cycles per request are the bridge's and the AXI model's hops, which
  the core seam does not contain.
- **More, where the testbench overlaps requests.** ``layernorm_32_packed``
  (+1,375; 1,537 loads and 1,536 stores of one or two words) and
  ``rmsnorm_32_w896_packed`` (+1,631; 1,793 + 1,792): back-to-back tiny
  requests, which the bridge's two credits overlap and the shim serialises.
  ``flash_attention`` (+6..+18) mixes both effects.

So the cycle difference is the memory model, not the core: the shim is a
different memory system from the testbench's, and the number is reported, not
gated (D-21). To make cycles comparable the shim would have to contain the
same memory path: instantiate MiniTPU's own ``uncore_io_tile`` (bridge +
landing FIFO, unmodified, ``src/ddr/``) between the core and an AXI4 slave
over the banks that answers as ``axi4_mem_model`` does at round trip 0. That
is RTL-only (no tool change) and is proposed for M-R2; it would also make the
``+ROUND_TRIP_CYCLES`` knob reproducible.

**Done (M-R2b, ``minitpu_rtl_m2b_2026-10-08.rst``):** with ``uncore_io_tile``
and a transcription of the TB's memory model in the shim, cycles equal the
testbench's on 52/52, digests still 52/52.

6. Findings
===========

Classes as in the U-matrices: **match**, **bug**, **missing abstraction**,
**workaround**, **semantic mismatch**.

M1. **match** -- a ``MemPort`` and stream ``Port``\ s on one ``RTLModule``
   run under ``target="simulator"`` (section 1), at 8 ports x 2**20 words
   (32 MiB of boundary memory) around the whole core: no
   change to ``allo/``.

M2. **match** -- an ``RTLModule`` composes in ``compose.Architecture`` when
   bound as a parameter (section 2). **Missing abstraction**, small: compose
   has no declaration category for an IP (``calls=`` takes functions only),
   so the object rides in ``parameters`` -- which compose otherwise means as
   numbers -- and no compose check knows the call's ports (that ``CORE``
   reads ``cmd`` and writes ``st`` is declared on the unit, not checked
   against the IP's ``Port`` directions). Proposal: ``Unit(ips=("CORE",))``
   whose check compares the call's stream arguments with the IP's
   ``input_idx``/``output_idx`` (``allo/ir/units.py`` already counts them for
   the region wiring check).

M3. **workaround** -- payloads <= 32 bits: the 256-bit DM word is eight
   ``MemPort``\ s and eight boundary arrays the host interleaves (bank k =
   bytes [4k, 4k+4) of each DM word), and the 128-bit bundle is four ``cmd``
   words. It costs no cycles (one DM word per cycle), only declarations.
   **Missing abstraction**: a wide or laned ``MemPort`` (``lanes=8`` over one
   array, or ``ctype`` up to 256 bits with a ``uint32`` host view).

M4. **workaround** -- fixed transfer counts: a non-persistent input stream
   needs a ``size`` (prefetch bound), so the program is a fixed 5,152 words,
   NOP-padded (bounded at 1,280 bundles; the largest oracle image is 1,208;
   IRAM holds 4,096). The shim consumes the padding in about 5k cycles per
   launch outside ``perf_cnt_cycles``. ``persistent=True`` would lift the
   bound but keeps the core out of reset across launches (the transactor
   resets once per thread-local model), which the testbench does not; the
   shim could add a soft reset, but a fresh model per call is the testbench's
   semantics for free. **Missing abstraction**: a ``size`` taken from the
   call (a length argument or an end-of-transfer marker).

M5. **missing abstraction** -- no run directory / plusargs for the model.
   ``$readmem`` paths resolve against the Python process's cwd, so the runner
   ``chdir``\ s the whole process around the call -- unsafe if anything else
   in the process uses relative paths concurrently, and silent when wrong
   (section 4 is the guard). Proposal: ``RTLModule(run_dir=...)`` (the
   transactor ``chdir``\ s around construction, where ``$readmem`` runs) or a
   ``+plusarg`` pass-through to ``VerilatedContext::commandArgs``. A
   ``$readmem`` warning should also be fatal by option.

M6. **missing abstraction** -- no build cache: the Verilated model is rebuilt
   in a fresh ``/tmp/rtl_*`` per ``RTLModule`` object, i.e. per process (70 s
   here at ``--build-jobs 16``; 253-430 s serial in M-R0). M-R2's gate runs
   pay it once per process; a cache keyed by the sources, flags and defines
   would make a re-run seconds.

M7. **semantic mismatch (recorded, not a defect)** -- the transactor is
   untimed with respect to the region: the drain copy and the status sink run
   after the call in their own threads. The cycle count comes from the core's
   counter, not from the region; the region gives no cycle number of its own.

M8. **match** -- ``max_stall`` (the follow-up's knob) was needed in
   principle: progress counts only handshakes and RAM accesses, and a core
   computing without memory traffic counts as stalled. At 20M no launch came
   near it; the shim's own ``MAXCYC`` is the run's timeout.

M9. Note on the plan: the plan named "``rtl/core_shim.sv`` + ``design.py`` +
   ``run.py``"; the task's names (``minitpu_core_shim.sv``,
   ``minitpu_rtl.py``, ``run_kernel.py``) were used. The plan's "``MemPort``
   larger than 4 words, ``uint32``, two kernels touching the same boundary
   array" open items: larger works (2**20); ``int32_t`` was used with
   ``uint32`` host views (no ``uint32_t`` run); only one kernel touches each
   bank.

Not exercised: the shim's DECERR path, ``MAXCYC`` timeout and partial-``wstrb``
counter (every launch was in-window, halted, full-strobe); ``program_id`` != 0.

7. What M-R3 needs from the tools
=================================

M-R3 (checkpoint 24) swaps the first unit: the Allo MXU inside the wrapped
core, held to the same oracle. ``mxu.sv``'s boundary to the VPU is
cycle-level -- ``vpu_ctrl_t`` pulses with no handshake on a fixed write-port
calendar, push -> valid 12/22/82 -- so a transaction-level call (one
``RTLModule`` call = run until ``done``, untimed against the region) cannot
host it. Three routes, in order of what they need:

1. **The Allo MXU as RTL inside the same Verilated model** (no new
   mechanism): Catapult or Vitis RTL of the U3 MXU behind ``mxu.sv``'s exact
   ports, substituted into the file list (``core_files()`` minus
   ``src/core/mxu/*`` plus the generated RTL and a port-compatible wrapper),
   the same shim, region and digests. Needs from the tools: (a) RTL at the
   shipped MXU's latencies, or the ``versions`` delta with a re-scheduled
   image (README D-21, queued behind Catapult II=1); (b) a port-compatibility
   check (``validate_rtl``'s ``--json-only`` reading, run on the substitute
   against ``mxu``'s pin list, including its packed/struct ports, which
   ``validate_rtl`` refuses at a *top* but must compare at a *submodule*);
   (c) a file-list helper in ``RTLModule`` (``replace={"mxu": [...]}``). The
   Vitis FPGA route (``minitpu-fpga-mxu``, started at checkpoint 24) is
   producing that RTL.
2. **The Allo MXU from the simulator, cycle-locked** (new mechanism): a
   Verilator DPI import (or a C++ module bound with ``--cc`` hierarchy
   ``public``) that calls Allo's compiled MXU step once per clock with the
   pulse inputs and returns its outputs the same cycle. Needs: (a) a
   per-cycle descriptor -- a wire/pulse port with no handshake and no
   ``size`` (``rtl_module.rst``'s "no scalar or wire sideband pins"); (b)
   aggregate pins (``vpu_ctrl_t``, 85 bits) packed into words by a generated
   adapter; (c) an Allo kernel callable as a *step function* (state
   persistent across calls -- ``Stateful`` -- with the MXU's own pipeline
   latency, not a dataflow region with threads); (d) one clock owner: the
   Verilated core drives the step, so the Allo side is never free-running.
3. **Two IPs in one region, lock-stepped** (largest): a multi-IP
   transactor sharing one clock across ``RTLModule`` objects (plan section
   3b) -- ruled out for M-R3 by its cost.

Route 1 keeps everything this milestone built (region, shim, oracle, runner)
and changes only the file list; it is the one to take first.
