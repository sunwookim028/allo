Tutorial: A PyTorch MLP on TinyTPU, Then Change It¶

This tutorial takes a two-layer PyTorch MLP, compiles it onto the TinyTPU with ACT, and runs it on the TinyTPU design itself. Then it changes the machine twice and runs the same model again:

  1. A parameter: a larger systolic array. One environment variable.

  2. An instruction: a new fused mvoutrelu, added to the ISA, the hardware and the compiler. Four small patches.

After each change ACT recompiles the unchanged model for the new machine, and the result is checked byte for byte against PyTorch. Nothing on this page needs Vitis. Every output shown is a real run, regenerated by make tutorial-outputs.

PyTorch nn.Module                 workloads/models.py
  -> AlloTracer + torch.fx        workloads/extract.py     shapes and ops
  -> one workload spec per layer                           act/corpus/'s JSON
  -> ACT mapspace search          act/search.py, act_target.py
  -> a TinyTPU program                                     checked on isa_ref
  -> the design, simulated        ip/, df.build(target="simulator")
  -> compared with PyTorch        workloads/run.py

Paths are relative to examples/tinytpu/. The flow and its design choices are explained on The Workload Suite: PyTorch MLPs on TinyTPU, the machine on TinyTPU-isa: A Programmable GEMM Accelerator.

Setup¶

Once per checkout. The allo conda environment, torch (optional upstream, required here) and this checkout’s own MLIR bindings:

conda activate allo
pip install --index-url https://download.pytorch.org/whl/cpu torch==2.14.0
export LLVM_BUILD_DIR=/path/to/llvm-project/build   # the env does not set it
examples/tinytpu/reproduce.sh --no-cosim   # builds mlir/build, runs the gates
cd examples/tinytpu

The Makefile exports LLVM_BUILD_DIR and OMP_NUM_THREADS if they are unset, and falls back to conda run -n allo when the shell’s python cannot import allo.

The model¶

An ordinary nn.Module, with nothing in it about Allo or the TinyTPU:

class MlpSmall(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(32, 32, bias=False)
        self.fc2 = nn.Linear(32, 16, bias=False)

    def forward(self, x):
        return self.fc2(torch.relu(self.fc1(x)))

It is registered with its batch size and input width, which is how make mlp MODEL=<name> finds it. A new model is a class and one line here:

MODELS = {
    "mlp_tiny": (MlpTiny, 4, 16),
    "mlp_deep": (MlpDeep, 4, 16),
    "mlp_small": (MlpSmall, 8, 32),
    "mlp_wide": (MlpWide, 64, 64),
    "mlp_bias": (MlpBias, 4, 16),
}

models.build fills the weights with integers in [-8, 8), so casting the model to int8 is exact. The suite measures a mapping, not a quantisation scheme.

Run it¶

make mlp                  # ~10 s: compile, build the design, run, compare

make mlp runs workloads/demo.py, which prints one section per stage. Each stage is a function in that file, so a script can reuse any of them.

Two checks are made here, and they catch different faults. The design against isa_ref, over the whole 4096-byte C buffer, catches the hardware. The model’s output against PyTorch catches the compiler and the flow. Most output bytes are saturated at 127 or -128, because weights and inputs in [-8, 8) summed over K=32 overflow int8. So the row comparison is weak evidence on its own, and the per-layer full-buffer check is the strong one.

make mlp MODEL=mlp_deep TOP=5     # four layers, five mappings each
make mlp-compile                  # stop after ACT; no design build

A model the machine cannot run is refused with the reason, not approximated:

  REFUSED fc1: nn.Linear with bias: the ISA has vadd but no mapping that broadcasts a bias row into the accumulator, so the baseline cannot express it
  REFUSED sigmoid: call_function torch.sigmoid is not an int8 GEMM or a fused ReLU; this build computes int8 x int8 -> int32 with a ReLU epilogue

The ISA has no instruction for the refused nodes, so the model does not compile.

Change 1: a larger array¶

The design’s parameters live in ip/params.py:

class TpuParams:
    """T is the only parameter that changes the *shape* of the region: the
    array is T*T instances and the chains are T and T*T stream arrays."""

    T: int = 4                  # SIMD width == array dimension
    MAXDIM: int = 64            # largest M, K, N supported
    SPAD_ROWS: int = None       # scratchpad rows, each one packed word
    NVR: int = None             # operand vector registers
    NAR: int = None             # accumulator vector registers
    QD: int = 16                # stream depth (16 since item 24: depth 8 deadlocks legal programs)
    IMEM_SIZE: int = 56         # instruction memory words, header included
    DMA_WORDS: int = 1          # packed words per operand-burst iteration

T is the array dimension, and the only parameter that changes the shape of the design: T*T processing elements and T- and T*T-wide stream arrays. Every size is derived from it. The shipped build reads TPU_T from the environment, so the change is:

TPU_T=8 make mlp          # an 8x8 array; ~25 s, the design is 4x larger

ACT searches again and finds different tilings, with half the loop trips:

Note

To change the shipped default rather than one run, edit it in both isa_spec.json (the T parameter) and microarch_isa.py, then python gen_isa.py --write. Editing only microarch_isa.py fails: isa_encoding.py, which isa_ref reads, is generated from the spec and keeps modelling a 4x4 machine, and gen_isa.py --check reports “the reference model would be modelling a different machine”. The two defaults are kept apart on purpose, so the design is checked against an ISA that was written down independently of it.

Change 2: a fused instruction¶

The vrelu and mvout at the end of every ReLU layer are two passes over the accumulator rows. mvout already clips each lane to int8 on its way out, so it can apply the ReLU in the same step: mvoutrelu. The change is four patches in tutorial/mvoutrelu/, in the order a designer would write them:

git apply tutorial/mvoutrelu/*.patch
python gen_isa.py --write
make mlp

Check it¶

make mlp is one model. Two gates check the instruction itself, and both passed on this change:

python gen_isa.py --check    # the spec, generated files and 9 consumers agree
python stress_isa.py         # ~3 min: 640 programs on the design vs isa_ref

Both earned their keep while the change was written. The first version failed each of them:

  • gen_isa.py --check failed twice. The accumulator’s clip no longer read as a literal saturation at -128, which is how the check verifies it. And dma_st, now reached by two opcodes, looked like it should decode them. It shouldn’t: both do the same thing there. That second failure was a gap in the check, which now lets a unit skip decoding when every opcode that reaches it has identical actions.

  • stress_isa.py deadlocked in kpn_model, a channel-level model of the design that had its own hand-written “only mvout sends a row to dma_st”. That rule is now derived from the spec’s actions.

  • stress_isa.py then found a real hardware bug: the accumulator read the source row from f1, the DRAM-row field, instead of f0. make mlp had passed anyway, because in its programs both fields are 0. Only the random programs exposed it. That is the line if op == OP_MVOUTRELU: read_row = f0 + row in step 2.

The first two fixes are part of the tree, so the patches above are just the designer’s change.

Undo it:

git apply -R tutorial/mvoutrelu/*.patch
python gen_isa.py --write

What is and is not established¶

  • Cycles on this page are estimates from ACT’s cost model, fitted to cosim at T=4. The fused instruction has not been through RTL cosim, and the T=8 figure is an extrapolation. make mlp-cosim MODEL=mlp_small measures either one (Vitis, one csynth, minutes).

  • The fused instruction is not on main. With the patches applied, the gemm.relu cases in tests/act/test_tinytpu.py fail, and should: they pin ReLU layers to the shipped vrelu; mvout programs, which cosim has measured. Merging mvoutrelu means measuring the new programs with TPU_TB=stress cosim and re-pinning those tests.

  • Untested combination: TPU_T=8 with the patches applied.

Reproducing this page¶

make tutorial-outputs                    # re-runs everything above, ~1 min
pytest tests/act/test_tutorial.py        # from the repo root, seconds

make tutorial-outputs runs tutorial/capture.sh, which writes the outputs this page includes to docs/source/designs/tinytpu_tutorial/. It applies the patches for the last run and reverts them however it exits. The test checks that the walk-through still compiles and matches PyTorch, that mlp_bias is still refused, and that the four patches still apply to the tree. If a file the patches edit moves on, that test fails first.
