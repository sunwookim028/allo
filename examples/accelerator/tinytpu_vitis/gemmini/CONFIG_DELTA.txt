Int8Dim4GemminiRocketConfig vs stock GemminiRocketConfig -- the COMPLETE field delta
====================================================================================

Written to be CHECKED, not believed. Every row cites the file and line that sets
the value; nothing here should be taken on trust. Read against the pins:

    chipyard                              e0207441
    generators/gemmini                    25809f7
    .../software/gemmini-rocc-tests       1a1a1c6

Paths are relative to the chipyard root. Two abbreviations:

    GC.scala   generators/gemmini/src/main/scala/gemmini/GemminiConfigs.scala
    C.scala    generators/gemmini/src/main/scala/gemmini/Configs.scala
    CC.scala   generators/gemmini/src/main/scala/gemmini/CustomConfigs.scala
    RA.scala   generators/chipyard/src/main/scala/config/RoCCAcceleratorConfigs.scala

Why the complete list and not the interesting subset: a silently inherited
default is the likeliest way two independent builds diverge for a reason nobody
can reconstruct afterwards. Section 3 is the part that matters most for that,
because those values are DERIVED -- two builds can agree on every written field
and still differ in hardware.


1. WHAT THE TWO CONFIGS ARE
---------------------------

  GemminiRocketConfig        RA.scala:10-14   -> gemmini.DefaultGemminiConfig
                                              -> GemminiConfigs.defaultConfig   (C.scala:21)
  Int8Dim4GemminiRocketConfig RA.scala:20-24  -> gemmini.GemminiCustomConfig(int8Dim4Config)
                                              -> defaultConfig.copy(...)        (CC.scala:60-66)

The two Chisel wrappers are STRUCTURALLY IDENTICAL -- both are
`case BuildRoCC => up(BuildRoCC) ++ Seq(...)`, i.e. both APPEND one Gemmini:

  DefaultGemminiConfig   C.scala:249-259
  GemminiCustomConfig    CC.scala:73-83

so the wrapper is not a source of difference. The surrounding SoC stack is
character-for-character the same in both classes:

  new freechips.rocketchip.rocket.WithNHugeCores(1)
  new chipyard.config.WithSystemBusWidth(128)
  new chipyard.config.AbstractConfig

(RA.scala:12-14 vs RA.scala:22-24). So the Rocket core, its 32 KiB L1 D$
(nSets 64 x nWays 8 x 64 B; generators/rocket-chip/src/main/scala/rocket/
Configs.scala:36-41), the 128-bit system bus, and the memory model
(WithBlackBoxSimMem(additionalLatency=0); chipyard AbstractConfig.scala:19 ->
HarnessBinders.scala:122-129) are identical on both sides.


2. WRITTEN FIELDS -- the complete diff (5 rows, of which 2 are no-ops)
----------------------------------------------------------------------

`int8Dim4Config` is `defaultConfig.copy()` with exactly five named arguments
(CC.scala:60-66). All five are listed, including the two that change nothing:

  field               stock      ours   set at                changes hardware?
  ------------------- ---------- ------ --------------------- -----------------
  meshRows            16         4      C.scala:31 / CC:61    YES
  meshColumns         16         4      C.scala:32 / CC:62    YES
  tileRows            1          1      C.scala:29 / CC:63    no -- same value
  tileColumns         1          1      C.scala:30 / CC:64    no -- same value
  has_training_convs  true       false  C.scala:48 / CC:65    YES, conv only

tileRows / tileColumns are restated at the value they already hold. They are
in the copy() for legibility, not to change anything. Stock defaultConfig sets
them to 1 at C.scala:29-30 and the case-class default is also 1 (GC.scala:26-27).

has_training_convs is read in EXACTLY ONE place in the whole generator:
LoopConv.scala:1358-1363, where it gates six conv-loop flags to constant false
(wrot180, input_dilated, trans_output_1203, trans_weight_1203,
trans_weight_0132, trans_input_3120). It is threaded there via
Controller.scala:153 and LoopConv.scala:1174/1538/1545. It is read NOWHERE in
LoopMatmul.scala, Mesh.scala, MeshWithDelays.scala, ExecuteController.scala,
Scratchpad.scala or AccumulatorMem.scala, and it does not appear in
GC.scala's generateHeader (GC.scala:275-500). A GEMM therefore cannot observe
it, and it is absent from gemmini_params.h. Verify with:
    grep -rn 'has_training_convs' generators/gemmini/src/main/scala/gemmini/

The four pipeline-depth fields are called out because they set fixed cost
directly and are the ones a reviewer will ask about: spad_read_delay 4,
tile_latency 0, mesh_output_delay 1, acc_latency 2. defaultConfig does NOT
override any of them -- they sit at their case-class defaults. For contrast
GemminiFPConfigs.defaultFPConfig sets spad_read_delay = 1 (ConfigsFP.scala:41),
tile_latency = 1..2 and mesh_output_delay = 0, so a materially shallower
Gemmini exists in-tree and was deliberately NOT used. Same for dataflow:
ours inherits Dataflow.BOTH although both benchmarks only ever pass WS, so
Gemmini carries an output-stationary datapath we never exercise
(the WS-only variant is leanConfig, C.scala:238).


3. DERIVED FIELDS -- where two builds can agree on the config and still differ
------------------------------------------------------------------------------

None of these is written anywhere. All are computed in the GemminiArrayConfig
body from the fields above, so they change when DIM changes even though no
field naming them was touched. This is the section to cross-check hardest.

I_TILE_BYTE_WIDTH and O_TILE_BYTE_WIDTH come out EQUAL at DIM=16 and DIM=4,
because DIM halves twice while ITYPE_BYTES/OTYPE_BYTES quadruple. Both must be
powers of two (require at GC.scala:239-241) and both are 16 / 64 at every DIM
in {2,4,8,16,32,64} for int8/int32, so that require never fires in this family.

Note that sp_capacity and acc_capacity are UNCHANGED (256 KB / 64 KB) while
sp_bank_entries and acc_bank_entries QUADRUPLE. The scratchpad is 256 KiB and
the accumulator 64 KiB at both DIMs; only the row shape changes. A 4x4 array
therefore gets the same on-chip memory as a 16x16 one.


4. GENERATED HEADER -- gemmini_params.h
---------------------------------------

The header is GENERATED, not written: Controller.scala:30 writes
config.generateHeader() to config.headerFilePath during Chisel elaboration, and
headerFilePath (GC.scala:505-524) resolves to
generators/gemmini/software/gemmini-rocc-tests/include/gemmini_params.h
whenever cwd is the chipyard root, which is how make launches sbt.

Fields that differ between the two configs (generateHeader GC.scala:337-347):

  #define DIM                 16      ->  4
  #define BANK_ROWS           4096    ->  16384
  #define ACC_ROWS            1024    ->  4096
  #define MAX_BLOCK_LEN       (64/(DIM*1))   ->  same expression, 4 -> 16
  #define MAX_BLOCK_LEN_ACC   (64/(DIM*4))   ->  same expression, 1 -> 4

Everything else in the header is identical, because it depends only on fields
section 2 shows unchanged: elem_t int8_t, acc_t int32_t, full_t int64_t,
BANK_NUM 4, scale_t float, MVIN_SCALE_IDENTITY 1.0, ACC_SCALE_IDENTITY 1.0,
ACC_READ_SMALL_WIDTH, ACC_READ_FULL_WIDTH, HAS_FIRST_LAYER_OPTIMIZATIONS.

TWO HAZARDS THAT MATTER FOR A CROSS-CHECK:

  (a) Every elaboration REWRITES THIS FILE IN PLACE. Elaborate a second config
      and the first one's header is gone, silently, with no error. Snapshot it,
      and rebuild the C tests immediately after each elaboration. Verify which
      hardware produced a number from the run's own banner -- both benchmarks
      print "GEMMINI DIM=%d elem_t_bytes=%d" as their first line.

  (b) rocc-tests HEAD (1a1a1c6) ships a header with DIM 16, BANK_ROWS 4096,
      ACC_ROWS 1024 and NO ACC_READ_FULL_WIDTH. The first three match stock
      GemminiRocketConfig; the missing ACC_READ_FULL_WIDTH does not, because
      defaultConfig sets acc_read_full_width = true (C.scala:157) and
      generateHeader emits the macro for it (GC.scala:485-486). That committed
      header was therefore generated by some LEANER config (leanConfig sets
      acc_read_full_width = false, C.scala:238), not by defaultConfig. Do not
      treat the committed header as the stock-config header; regenerate it.

  (c) Header-only regeneration, no build: GEMMINI_ONLY_GENERATE_GEMMINI_H=1
      makes Controller.scala:31 System.exit(1) right after the write, so
          GEMMINI_ONLY_GENERATE_GEMMINI_H=1 make -C sims/verilator firrtl CONFIG=<X>
      writes the header and then fails on purpose. ~1 minute. This is the
      pattern generators/gemmini/scripts/build-spike.sh:20-24 uses.


5. THE SECOND MATCHED POINT (DIM=8)
-----------------------------------

int8Dim8Config (CC.scala:82-88) is the same delta again: meshRows/meshColumns 8,
tileRows/tileColumns 1, has_training_convs false. Its derived values follow the
same formulas -- BANK_ROWS 8192, ACC_ROWS 2048, sp_width 64, cisc_dim 4,
ITYPE_BYTES 2, OTYPE_BYTES 8, I_TILE_BYTE_WIDTH 16, O_TILE_BYTE_WIDTH 64.
Elaborated as Int8Dim8GemminiRocketConfig (RA.scala, beside the DIM=4 class).

For a DIM=16 point to be a CONSISTENT third member of this family it must set
has_training_convs = false. Stock GemminiRocketConfig leaves it true
(C.scala:48), which is the only field besides the mesh that separates it from
this family, and it is exactly the kind of silently inherited default that
would make a disagreement between two independent builds untraceable.
